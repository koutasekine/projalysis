# プロジェクト分析(projalysis.sapp.jp)仕様書

版 0.52(2026-10-29)

この文書は、アプリの外から見た仕様(読み込み、対応づけ、計画書分析、作業分析、サマリー、画面、保存)を定める。実装の作り方は、計算部の取り込み(12 章)を除いて定めない。実装は index.html(単一 HTML)で、この仕様書に沿って作る。

## 1 章 目的と範囲

### 1.1 目的

プロジェクト計画(plan.sapp.jp)で書いた計画書(`.plan`)と、マイログ(mylog.sapp.jp)で書いた各メンバーの記録(`.mylog`)を読み、計画書の変更と、チームの作業の進み具合を、決まった形の表と図で出す。分析は次の 2 つからなる。

- **計画書分析**(5 章): 複数の `.plan` を版として並べ、変更箇所と変更履歴を示す。
  - 版を `version:` の日付の順に並べ、変更履歴を追えるようにする。
  - 選んだ 2 つの版の間で、何が増え、何が消え、何が変わったかを示す。
  - 書式が人によって変わらないので、比べた結果を読む側(採点者など)の手間が減る。
  - 計画が版を追ってどう変わったか(延び・範囲・進み・計画が不安定だった部分・負担の偏り)を図で示し、作った人(学生・PM)自身が振り返れるようにする。
- **作業分析**(6 章): チームの全員のマイログと計画書を突き合わせ、作業の集計と、問題の兆候、計画書に書き写す候補を示す。
  - 計画書に書き写す候補(状態の変化、テストで確かめた MOP)を一覧にし、計画書の版を記録に合わせられるようにする。
  - 詰まっている人、放置されている依頼、止まっているタスクなど、運営の問題を事実として拾い出す。
  - 講義の「プロジェクトのデータ」(人ごと・タスクごとの作業時間、進捗率、TRL・TPM の推移、テストの実施日と結果)の表と図を作る。

読み込んだ計画書とマイログは、1 つの plans(9.1 節)に保存する。次に開いたときは、そのファイルを開けば同じ一覧から見られる。

### 1.2 範囲

- 計画書だけ、マイログだけ、その両方の、どれでも読める。計画書だけなら計画書分析、マイログだけなら計画を使わない作業分析(複数人のマイログを読める。計画を使う表と兆候は出ない)、両方ならすべてのビューが出る。どのアプリをどう組み合わせるかは定めない(使う人が決める)。README と使い方に、ほかのアプリとの関係と、プロジェクト分析を使う組み合わせの例を書く。
- 読むだけのアプリとする。`.plan` と `.mylog` は読むだけで、書き換えない。テキスト欄と、記録を書く画面は持たない。
- アプリが書くファイルは plans(9.1 節)だけである。中身は、読み込んだファイルを組み合わせただけのものとする。
- `.plan` の解析と日程の計算は、プロジェクト計画と同じ計算部で行う(3.2 節)。記法の規則はプロジェクト計画の仕様書による。`.mylog` の解析と照合は、マイログと同じ計算部で行う(3.8 節)。記法の規則はマイログの仕様書による。
- 計画書分析は `.plan` だけを使う。
  - 要素は名前で対応づける(4 章)。名前の似た要素を推測して対応づけることはしない。
  - `.plan` には実績の日付がない。日程の比較は、各版のテキストから計算した予定どうしの比較である。
  - 実績の日付と作業時間は扱わない。変化は版の単位でとらえ、「どの版から変わったか」を示す。あるタスクが初めて完了になった版から、完了の時期をその版と前の版の日付の間に絞れる(5.11 節)。
- 作業分析は、マイログの記録(実績の日付と作業時間)を使う。
  - チームとして決めたこと(講義中に確かめたテストの結果、TRL・TPM など)は、チームの誰かが自分のマイログに書く。
  - 人に聞く・頼むのは、チームの人(計画書の `members:` にいる人)への `ask:`・`review:` だけとする。チームの外の人に助けを求める記録は扱わない。
  - 進捗率は本人の主観の値として扱い、見積もりには使わず、止まっていることの検知にだけ使う(マイログの仕様書 1.2 節と同じ)。
  - 追記を見つける機能は持たない。
- 計画書への反映は、利用者がプロジェクト計画で行う。このアプリは候補を示すだけとする。
- 事実だけを出す。変更の理由・影響の解釈・所見は出さない(利用者が自分で考えて書く)。
- 使う人と使い方は定めない。

### 1.3 S Apps としての前提

- 単一 HTML で、サーバーにデータを送らず、ネットなしで動く。
- 外部ライブラリを読み込まない。
- アプリ本体に Node.js を含めない。ビルドと検査に使うのはよい。
- 必ず同じ表と図を出す(決定的)。計画書分析は、同じファイルの一覧から同じ表と図を出し、表示する日の日付には依存しない。作業分析と、サマリーの作業の概要(7.2 節)は、同じファイルの一覧と同じ基準日(6.2 節)から同じ表と図を出す。
- ライセンスは MIT とする。

### 1.4 名前

- アプリ名(上の帯・タブの題名): プロジェクト分析
- 公開先: projalysis.sapp.jp
- リポジトリ名: projalysis
- チームログ(teamlog)は別のアプリとしては作らず、このアプリの作業分析とした。

## 2 章 用語

プロジェクト計画の仕様書 2 章の用語(節・根・要素・末端・途中の要素・タスク・属性・エラー・警告など)と、マイログの仕様書 2 章の用語(マイログ・設定の行・日付の行・記録の行・記録先・計画にない作業・照合する版・依頼・兆候・週・記録者・作業日数・合計時間・記録日数)は、そのまま使う。

画面では、下の表の「増えた」「消えた」「変わった」「前の版」「後の版」を、それぞれ「追加」「削除」「変更」「変更前」「変更後」と表記する。画面では状態を「進捗」と表示する(3 つのアプリで同じ。下の表の「状態」)。画面の文言は簡潔にする。人については、チームにいる人そのもの(`members:` の並び・メンバーの増減・個人の休み)を「メンバー」、タスクに割り当てられた人(作成者・確認者・担当者ごとの作成の日数・担当なし)を「担当者」と表記する。

| 用語 | 意味 |
|---|---|
| 版 | 読み込んだ `.plan` 1 つ |
| 版の日付 | その `.plan` の 1 行目の `version:` の日付 |
| 版の名前 | 画面と表で版を示す名前(3.5 節)。例: 「2026-10-27 版」「2026-10-27 版 (2)」 |
| 計画書 | プロジェクト計画の `.plan`。読み込んだ計画書の 1 つ 1 つを版と呼ぶ |
| 一覧 | 読み込んだ版の並び(3.4 節)。マイログの一覧と区別するときは「計画書の一覧」と書く |
| plans | 計画書の一覧とマイログの一覧をまとめて保存するファイル(9.1 節)。拡張子は `.plans` |
| 比べられる版 | エラーがなく、版の日付がある版(3.6 節) |
| 前の版・後の版 | 比べる 2 つの版のうち、一覧で前にあるものと後ろにあるもの(5.2 節) |
| 対応名 | 対応づけに使う名前。根を除いた祖先と自分の名前を `::` でつないだもの(4.1 節) |
| 対応する | 前の版と後の版で、同じ要素とみなすこと(4 章) |
| 増えた | 後の版にだけある |
| 消えた | 前の版にだけある |
| 移動 | 名前が同じで、親が変わった(4.3 節) |
| 変わった | 対応するタスクの属性の値が違う(5.4 節) |
| 隣り合う版 | 比べられる版だけを一覧の順に並べたとき、隣り合う 2 つの版 |
| 第 1 層の要素 | WBS の根の子。工程(フェーズ)とは限らない |
| 状態 | タスクの進み具合(実行前・実行中・完了・問題発生)。`status:` で書く。画面では「進捗」と表示し、今の状態(報告がなければ計画の値)・最後の状態(報告だけ)・計画の状態(計画の `status:`)を「今の進捗」「最後の進捗」「計画の進捗」と表示する(プロジェクト計画・マイログと同じ) |
| タスク | WBS の末端の要素(プロジェクト計画の仕様書 2 章) |
| 作業 | タスクを含む、マイログに記録されるすべての仕事。計画にない作業、機能のテスト・TRL・TPM、確認や質問への対応を含む |
| 計画書分析 | 計画書の版どうしを比べる分析(5 章)。マイログは使わない |
| 作業分析 | マイログと計画書を突き合わせる分析(6 章) |
| マイログの一覧 | 読み込んだ `.mylog` の並び(3.7 節) |
| 対応 | 依頼に、相手が返事(`reviewed:`・`answered:`)を書いたこと(6.5 節) |
| 基準日 | 作業分析で、日数を数え、記録を数える範囲を決める日(6.2 節) |
| 基準日の版 | 作業分析で使う計画書の版(6.2 節) |

作業分析(6 章)の「メンバー」は、マイログの `by:` と、基準日の版の `members:` にいる人とする(6.1 節)。

## 3 章 読み込み

### 3.1 読めるファイル

| 拡張子 | 扱い |
|---|---|
| `.plans` | plans(9.1 節)。計画書の一覧とマイログの一覧を、plans の中身で入れ替える。保存していない変更があれば、破棄してよいかを確かめる |
| `.plan`・`.txt` | プロジェクト計画のテキスト(`.txt` は、プロジェクト計画がファイル操作機能のないブラウザで保存したもの)。計画書の一覧に足す(3.3 節) |
| `.mylog` | マイログのテキスト。マイログの一覧に足す(3.7 節) |
| `.svg` | 下の項目 |

- 開く(ファイル選択で複数選べる)・ファイルを追加・ファイルを置く(複数をまとめて置ける)は、どれも上の表のとおりに扱う。一度に違う種類を混ぜてよい。`.plans` と一緒に開いた・置いたほかのファイルは、入れ替えた後の一覧に足す。`.plans` は、読めることを確かめてから破棄の確認を出す(読めなければ確認を出さずに知らせる)。入れ替えを取りやめたときは、一緒に開いた・置いたファイルも足さない。
- 一度に開いた・置いたファイルに `.plans` が 2 つ以上あれば、`.plans` は開かずに「plans は 1 つずつ開いてください」と知らせる(ほかのファイルは足す)。
- プロジェクト計画の版 0.30 までに「画像…」で保存した SVG(テキストを埋め込んだもの)も、埋め込まれた `.plan` を 1 つの版として読む。ファイル名は「SVG の名前.plan」とする。プロジェクト計画の版 0.31 以降で保存した SVG にはテキストが入っていないので読めない。読めないときは「この SVG には .plan が埋め込まれていません(開ける .svg は、プロジェクト計画の版 0.30 までに「画像…」で保存したものだけです)」と知らせる。
- チームログで保存した `.teamlog` は読まない(チームログは公開していないため)。
- `.zip` は読まない。置かれても何もせず、知らせもしない。フォルダを置いて中のファイルを読む機能は持たない。
- 文字コードは UTF-8 とする。BOM があれば除く。改行は LF と CRLF のどちらも読む。
- そのほかの開けない拡張子のファイルは、開けないことを知らせて読まない。

### 3.2 計算部

- `.plan` は、プロジェクト計画の計算部(core.js の `/*CORE-BEGIN*/` 〜 `/*CORE-END*/`)の `analyze` で読む。
- `.mylog` は、マイログの計算部(logcore.js の `/*LOG-BEGIN*/` 〜 `/*LOG-END*/`)で読む(12 章)。
- 読み込むすべての版を、同じ版の計算部で読む。
- 計算部の版を画面には書かない。

### 3.3 足す

- `.plan` は、計画書の一覧に足す。一覧を入れ替えるのは、`.plans` を開いたときだけとする(3.1 節)。
- テキストが一覧のどれかと 1 文字も違わない `.plan` は足さず、「同じ内容のため追加しませんでした: ファイル名(同じ内容のファイル名 と同じ)」と知らせる(例: 「b.plan(a.plan と同じ)」)。`version:` の日付だけが違うものは、別の版として足す。
- ファイル名が同じでテキストが違う `.plan` は、別の版として足す。
- 一覧の各版には外すボタンを付け、押すと一覧から除く。

### 3.4 一覧の並び

- 版の日付の古い順に並べる。
- 同じ日付の版の中の並びは、次のとおりとする。
  - 先に一覧にあった版を前、後から足した版を後ろにする。
  - 一度に複数を足したときは、足した順(ファイル選択や置いたときに渡された順、plans の中の順)とする。
  - 同じ日付の版の中だけ、手で並べ替えられる。日付をまたいで動かすことはできない。並べ替えるボタンは、各版に付けた上へ(▲)・下へ(▼)とする。
- 手で並べ替えた順は、plans・自動保持に残す。
- 版の日付のない版(3.6 節)は、一覧の最後に、足した順に並べる。

### 3.5 版の名前

- 「YYYY-MM-DD 版」とする。
- 同じ日付の版が 2 つ以上あるときは、一覧の並びの順に 2 つ目から「YYYY-MM-DD 版 (2)」「YYYY-MM-DD 版 (3)」…とする。1 つ目には番号を付けない。
- 番号は、比べられる版(3.6 節)だけで数える。比べられない版は、日付があっても「YYYY-MM-DD 版」とし、番号を付けない。
- 番号は並べ替えると付け直す。
- `version:` の行は比較の対象にしない。版の違いは版の名前で示す。

### 3.6 比べられない版

- エラー(プロジェクト計画の仕様書 5.3 節・10 章)のある版は、一覧に並べ、エラーの件数と、最初のエラー(行の番号がいちばん小さいもの)の行と文を示す。比べる表と照合からは外す。一覧には「エラー N 件(行: 文)。比較と照合から除外」と示す。
- `version:` が正しくない場所にある版は、計算部が構文エラーとするので、上と同じ扱いになる。
- `version:` のない版は、版の名前を「version: なし」とし、一覧に「version: がないため比較と照合から除外」と示し、比べる表と照合からは外す。
- 警告だけの版は、比べられる版として扱う。一覧には警告の件数を示す。

### 3.7 マイログの一覧

- 足した順に並べる。各マイログに、`by:` の名前・ファイル名・`version:`・最後の日付の行の日付・診断の件数(エラーがあればエラー)・外すボタンを示す。上へ(▲)・下へ(▼)のボタンで並べ替えられる。
- テキストが一覧のどれかと 1 文字も違わない `.mylog` は足さず、「同じ内容のため追加しませんでした: ファイル名(同じ内容のファイル名 と同じ)」と知らせる(3.3 節の `.plan` と同じ)。
- `by:` が一覧のどれかと同じで、テキストが違う `.mylog` を足したときは、アプリの中のダイアログで「(名前)のマイログがすでにあります(ファイル名、version: 日付)。」と出し、「置き換える」「両方残す」「やめる」から選ばせる。アプリが自動で選ぶことはしない。
  - 「置き換える」は、一覧の同じ位置で入れ替える。新しく集めたマイログで集計し直すときに使う。
  - 「両方残す」を選んだときは、両方を集計に使い、要確認の先頭に「同じ人(名前)のマイログが 2 つあります」と出す。外すボタンで外すまで出し続ける。
  - 一度に複数を置いたときは、1 つずつ尋ねる。尋ねている間に置いた・選んだファイルは、答えた後に、置いた順に開く(1 つの答えが別のマイログに当たらないようにするため)。
- エラーのあるマイログは一覧に並べ、エラーの件数と最初のエラー(行と文)を示し、集計と兆候から外す。要確認の先頭に「エラーのため集計から除外: ファイル名」と出す。
- エラーのあるマイログしかない人は、マイログのない人(6.1 節)とはせず、S1 に出さない。依頼の相手がその人なら、依頼の状態と S3 に「相手のマイログにエラーがあり、集計から外しています」と添える。
- マイログの警告は、一覧に件数だけを示す。件数を押すと、そのマイログの診断の一覧をダイアログで示す。
- マイログの診断(今日より後の日付の警告など)の「今日」は、表示する日の日付とし、基準日(6.2 節)にはよらない。基準日を過去にしても、一覧の警告は変わらない。
- 一覧は折りたためる。

### 3.8 照合

- マイログの記録先は、マイログの仕様書 3.7 節・5.4 節の規則で決める(日付の行ごとに照合する版を選ぶ)。
- 照合は、各マイログの日付の行ごとに選ぶ版で行い、基準日(6.2 節)にはよらない。
- 集計・兆候・反映候補(6 章)では、記録先を基準日の版の要素に寄せる(マイログの仕様書 5.6 節)。隣り合う版ごとに 4 章の対応(対応名・根・移動)でたどり、移動したタスクの記録は、移動の後のタスクの記録とする。計画にない作業だった記録は、基準日の版でその名前の要素がちょうど 1 つに決まれば、その要素の記録とする。境界は 4 章と同じで、名前の変更は推測しない(4.4 節)。
- 集計(6.6 節)では、記録先を対応名で分ける。たどれない記録先(名前を変えた要素など)は別の行になる(マイログの仕様書 5.5 節・5.6 節)。

## 4 章 対応づけ

### 4.1 対応名

- FBS・PBS・WBS の要素は、節ごとに、対応名が同じものを対応させる。
- 対応名は、根を除いて、祖先の名前と自分の名前を上から順に `::` でつないだものである。例: WBS の根「カレンダーアプリ」の下の「設計フェーズ」の下の「画面設計」の対応名は `設計フェーズ::画面設計`。
- 名前の大文字と小文字、全角と半角は、計算部と同じく区別する。
- メンバーは名前で対応させる。

### 4.2 根

- FBS・PBS・WBS の根は、名前によらず、前の版の根と後の版の根を対応させる。
- 根の名前が違うときは、節ごとに「FBS の根の名前を変更: 前の名前 → 後の名前」の 1 行を出す(5.3 節)。
- 一方の版にしかない節(FBS・PBS は省略できる)は、その節の要素がすべて増えた、または消えたとする。

### 4.3 移動

- 4.1 節で対応しなかった要素のうち、同じ節の消えた側と増えた側に、名前(対応名ではなく、要素自身の名前)がまったく同じものがちょうど 1 つずつあれば、その 2 つを対応させ、移動とする。
- 同じ名前が片側に 2 つ以上あるときは、移動とせず、消えた・増えたのままにする。
- 移動の判定は、上の要素から順に(前の版の木の順に)行う。
- 移動した要素の子は、親の対応名が変わるので 4.1 節では対応しない。子にも同じ規則を当てる。
- 移動は、表では「移動(親: 前の親の対応名 → 後の親の対応名)」と示す。親が根のときは「(根)」と書く。

### 4.4 推測しないこと

- 名前の似た要素、属性の似た要素を推測して対応させることはしない。名前の変わった要素は、消えた 1 行と増えた 1 行で出す。

### 4.5 対応した要素の数

前の版と後の版の間で、節ごとに次の形で示す。

- 「対応した数 / 2 つの版のどちらかにある要素の数」(両方にあるものは 1 つと数える)。
- 数える節は FBS・PBS・WBS とメンバーである。
- 木のすべての要素(途中の要素を含む)を数え、根は数えない。
- 移動は、対応したと数える。
- 一方の版にしかない節は、対応した数を 0 とする。どちらの版にもない節は出さない。

### 4.6 MOP

- 対応した FBS の要素(移動を含む)どうしで、MOP の文が 1 文字も違わないものを対応させる。
- 同じ要素に同じ文の MOP が複数あるときは、書いた順に対応させる。
- 対応した MOP のうち、前の版で `mop:`、後の版で `mop*:` のものを「チェック済みになった」、その逆を「チェックを取り消した」とする。
- 対応しなかった MOP は、増えた・消えたとする。文の書き換えは、消えた 1 行と増えた 1 行になる。
- 増えた・消えた FBS の要素の MOP は、その要素の行に含めて示し、MOP の増えた・消えたには数えない。

## 5 章 計画書分析

計画書の版どうしを比べる。マイログと基準日は使わない。

### 5.1 版の概要(全版)

サマリーのビュー(7 章)の最初の表である。比べられる版すべてを、一覧の順に列に並べる表とする。行は次のとおり。

| 行(画面の表記) | 値 |
|---|---|
| 版 | 版の名前 |
| ファイル | ファイル名 |
| 開始日 | `start:` |
| 期限 | `end:`(なければ「―」) |
| 全体の休み | `off:` の値(注を除いた書いたままの文。なければ「―」)。太字にするかは、カンマで区切った値を、値の中の空白(`..` の前後を含む)を除いて並べ替えて比べる(空白や並びだけの違いは変わったとしない) |
| クリティカルパスの長さ(日) | 日数(プロジェクト計画の仕様書 6.2 節) |
| 日程の長さ(日) | 担当を入れた日程の暦日数(同 6.4 節) |
| 終了日 | 担当を入れた日程の最後の日付 |
| メンバー数 | `members:` の人数 |
| FBS の要素の数 | FBS の木の要素の数(途中の要素を含み、根は数えない。4.5 節と同じ。FBS がなければ「―」) |
| PBS の要素の数 | 同上(PBS) |
| WBS の要素の数 | 同上(WBS)。タスク(末端の要素)と途中の要素の合計 |
| タスク数 | タスクの数 |
| 総日数 | タスクの `days:` の合計 |
| MOP 総数 | FBS の要素に書いた MOP の数(`mop:` と `mop*:` の合計。FBS がなければ「―」) |
| チェック済みの MOP 数 | そのうち `mop*:` の数(FBS がなければ「―」) |
| 警告数 | 警告の数 |

- 左の版と値が違うセルは、太字にする。
- エラーのある版と版の日付のない版は、列に入れない。
- 列が多すぎて縮みすぎるときの印刷は、9.5 節による。

### 5.2 比べる 2 つの版

- 比べられる版から 2 つを選ぶ。一覧で前にある方を前の版、後ろにある方を後の版とする。
- 既定は、比べられる版のうち一覧の最初と最後である。利用者が選ぶまでは、版を足す・外す・並べ替えるたびに既定に従う。
- 利用者が選んだ後は、選んだ 2 つを残す。選んだ版が外れたとき(外した、比べられなくなった)は、既定に戻る。
- 比べられる版が 2 つ未満のときは、5.3 節〜5.7 節・5.10 節の代わりに「比較には 2 つ以上の版が必要です」と出す。
- 選んだ 2 つは自動保持に残し、plans には残さない。plans を開いたときは既定の 2 つとする。

### 5.3 比較の要約

5.4 節〜5.7 節の先頭に置く。

- 前の版と後の版の版の名前とファイル名。
- 根の名前の変更(4.2 節)。変更がなければ出さない。
- 対応した要素の数(4.5 節)の表。

### 5.4 WBS

タスク(WBS の末端の要素)について、次の 4 つを示す。ビューの名前は「WBS」とするが、途中の要素は示さない(下の項目)。

1. **増えたタスク**: 対応名、日数、作成者、確認者。
2. **消えたタスク**: 対応名、日数、作成者、確認者。
3. **移動したタスク**: 対応名(後の版)、前の親と後の親。
4. **変わったタスク**: 対応するタスク(移動を含む)で、次の項目の値が違うもの。
   - 日数(`days:`)
   - 作成者(`by:`)・確認者(`review:`)・対象(`for:`): 親から受け継いだ後の値で比べる。
   - 先行(`after:`): そのタスクと祖先に書いた `after:` が指す要素をすべて集めたもので比べる。途中の要素を指したものは、その要素のまま比べ、下のタスクには広げない。
   - 状態(`status:`)
   - メモ(`note:`)

- 対象(`for:`)と先行(`after:`)は、指す要素どうしを 4 章の対応で比べる。指す要素が移動しただけなら、変わったとしない。指す要素の名前が変わった(対応しない)ときは、変わったとする。
- 作成者・確認者・対象・先行は、並びの順によらず、集まりとして比べる。
- 状態の変化は、ほかの項目とは別の表にまとめる。状態だけが変わったタスクは、変わったタスクの一覧には入れず、状態の変化の一覧にだけ入れる。
- 表は 1 項目 1 行とし、列は「タスク・項目・前の版・後の版」とする。同じタスクの行はまとめたセルにする。
- タスクが途中の要素になった(子が付いた)ときは、消えたタスクの行に「(子要素ができた)」と添え、子は増えたタスクとする。途中の要素がタスクになった(子がなくなった)ときは、増えたタスクの行に「(子要素がなくなった)」と添える。
- WBS の途中の要素の増えた・消えた・移動は、この表には出さず、対応した要素の数(4.5 節)にだけ表れる。
- 行の並びは、増えたタスクと移動・変わったタスクは後の版の木の順、消えたタスクは前の版の木の順とする。

### 5.5 日程

- 対応するタスク(移動を含む)について、前の版と後の版の終了予定日を日付で並べ、ずれを暦日の日数で示す(後 − 前。遅れは +、早まりは −)。
- 終了予定日は、各版の担当を入れた日程(プロジェクト計画の仕様書 6.3 節)で計算したものとする。
- 表の上に、いちばん遅れたタスクを、タスクとずれの表で示す。ずれの最大が同じタスクが複数あれば、すべて示す。ずれの最大が 0 以下なら「遅れたタスクはありません」とする。
- 表の題は「タスクごとの終了予定日」とし、列は「タスク・変更前・変更後・差(日)」とする。
- 行の並びは後の版の木の順とする。

**G. 見積もりの変化**

- タスクごとの終了予定日の表の下に置く。図の上に「比較: 変更前の版 → 変更後の版」を書く(この図だけを保存したときにも、どの版の比較かがわかるようにするため)。
- 対応するタスク(移動を含む)について、前の版と後の版の日数を、タスクごとに 2 本の横棒で並べる(前の版は薄い灰、後の版は黒枠)。差を数で添える。
- 棒の上に凡例(灰: 変更前、黒枠: 変更後)を置く(図だけを保存しても棒の意味がわかるように)。
- 図の上に、次の 3 つの数を書く。
  - 追加したタスクの割合: 増えたタスクの日数の合計 ÷ 後の版のタスクの日数の合計(百分率の整数)
  - 消えたタスクの日数の合計
  - 対応するタスクの日数の合計の前・後
- 行の並びは、後の版の木の順とする。

### 5.6 FBS・PBS・MOP

- FBS の要素: 増えた・消えた・移動。途中の要素を含む。
- PBS の要素: 増えた・消えた・移動。途中の要素を含む。
- FBS の増えた・消えた要素の表は、要素(対応名)と MOP の列とする。MOP は、その要素の MOP をすべて「 / 」で区切って並べ、チェック済みには ✓ を付ける。MOP がなければ「なし」とする(4.6 節)。
- MOP(4.6 節): 増えた・消えた・チェック済みになった・チェックを取り消した。列は「FBS の要素(対応名)・MOP」とする。
- 節がどちらの版にもないときは、その部分を出さない。

### 5.7 メンバー

- 増えたメンバー、消えたメンバー(画面の表は「追加したメンバー」「削除したメンバー」)。
- 両方の版にいる担当者ごとに、作成の日数(作成者になっているタスクの日数の合計。プロジェクト計画の仕様書 7.7 節)の前・後・差。
- `by:` のないタスクがどちらかの版にあれば、「(担当なし)」の行を置く。
- 個人の休み(`off:`)が変わったメンバー(画面の表は「休みを変更したメンバー」)は、前・後の値(注を除いた書いたままの文)を示す。変わったかどうかは、カンマで区切った値を、値の中の空白(`..` の前後を含む)を除いて並べ替えて比べる(空白や並びだけの違いは変わったとしない)。
- 行の並びは後の版の `members:` の順、消えたメンバーは前の版の順とする。

### 5.8 数の書き方

- 日数は、プロジェクト計画と同じく小数を書ける(`1.5` など。末尾の 0 は書かない)。
- 日付は `YYYY-MM-DD` とする。
- 何もないときは「なし」と書く。
- 表の外の文は、一定の幅で折り返す(長い 1 行で図の幅が広がり、印刷で縮みすぎないため)。表のセルの文も、列の幅の上限で折り返す。

### 5.9 推移(全版)

比べられる版すべてで描く図である。比べる 2 つの版の選択には依存しない。上から次の 5 つの図と、5.11 節の表を並べる。

- 横軸は、E を除き、版の並び(比べられる版を一覧の順に等間隔に置く)とし、目盛りの文字は版の名前とする。
- 比べられる版が 1 つのときは、A・D・E・H は点 1 つで描き、I は「変更の多い部分: 2 つ以上の版が必要です」とする。

**A. 終了日の推移**

- 縦軸は日付とする。版ごとに、担当を入れた日程の終了日(プロジェクト計画の仕様書 6.4 節)を点で打ち、線でつなぐ。
- `end:`(期限)のある版は、その版の位置に期限の印を打ち、期限の印どうしを点線でつなぐ。期限の印と点線は強調の色(えんじ)とする。
- 第 1 層の要素ごとの終わりの線は描かない(第 1 層の要素は版によって名前が変わり、線が途切れるため)。

**E. バーンアップ(範囲と完了の推移。画面の題は「バーンアップ(横軸は版の日付)」)**

- 横軸は版の日付とし、暦日で等間隔に目盛る。同じ日付の版が複数あるときは、その日付の一覧で最後の版で代表させる。
- 縦軸は日数とし、目盛りは少なくとも 0〜1 日とする(タスクの日数がすべて 0 のときも)。版ごとに「タスクの日数の合計」と「状態が完了のタスクの日数の合計」の 2 本の線を引く。
- 2 本の線は線の形(実線・点線)で区別し、線の端に名前を書く。

**D. タスクの数と状態の推移(画面の題は「タスク数と進捗の推移」)**

- 版ごとに 1 本の棒を立て、タスクの件数を状態(実行前・実行中・完了・問題発生)で積み上げる。棒の高さの全体がタスクの件数である。
- 積み上げの色は、プロジェクト計画のガントチャートと同じ状態の色(実行前は白地に黒枠、実行中は青、完了は薄い灰、問題発生はえんじ)とする。図の上に凡例を置く。
- 積み上げの順は、下から完了・実行中・問題発生・実行前とする。
- FBS のある版は、棒の下に「MOP チェック済みの件数 / MOP の件数」を書く。

**I. 変更が多かった部分(WBS の第 1 層の要素ごと。画面の題は「変更の多い部分(WBS の第 1 層ごとのタスクの変更数)」)**

- 行を第 1 層の要素、列を隣り合う版の組とする表とし、各セルに、その組の間で増えた・消えた・移動した・変わったタスク(5.4 節。状態だけの変化は含めない)のうち、その第 1 層の要素の下にあるものの件数を書き、件数に応じて灰色の濃淡で塗る。
- タスクがどの第 1 層の要素の下にあるかは、増えた・移動した・変わったタスクは後の版で、消えたタスクは前の版で決める。タスクが根の直下にあるときは、そのタスク自身とする。第 1 層の要素は名前で対応づけ(4.1 節)、名前の変わった要素は別の行とする。
- 行の並びは、その要素が初めて現れた版の木の順とする。
- 左の欄の幅は、見出し(「WBS の第 1 層」)と行の名前が収まる幅とし、上限を 240 px とする。収まらない名前は先頭の側を「…」で縮める。列の幅は、版の名前が収まる幅(少なくとも 120 px)とする。
- 最後の行に、組ごとの合計を置く。

**H. 担当者ごとの作成の日数の推移(画面の題は「担当者ごとの作成の日数」)**

- 縦軸は日数とし、目盛りは少なくとも 0〜1 日とする。担当者ごとに、各版の作成の日数(5.7 節)を点で打ち、線でつなぐ。その版にいない担当者は、線を切る。
- 線はすべて黒とし、線の右端に担当者の名前を書く。名前が長いときは、幅 160 px に収まるよう先頭の側を「…」で縮める。
- `by:` のないタスクがある版があれば、「(担当なし)」の線を置く。

### 5.10 ガントチャート(2 つの版)

比べる 2 つの版(5.2 節)で描くガントチャートの比較である。先頭に 5.3 節の要約を置く。見積もりの変化(G)は 5.5 節に置く。

**F. ガントチャートの比較**

- タスクごとに、前の版の棒と後の版の棒を上下に並べる。前の版の棒は薄い灰、後の版の棒は黒枠とする。
- 棒の位置は、各版の担当を入れた日程(プロジェクト計画の仕様書 6.3 節)による。目盛りは日付とし、2 つの版の期間をすべて含める。今日の線と状態の色は描かない。
- 休みは、プロジェクト計画のガントチャートに合わせて描く。変更後の版の全体の休みの日は灰の地(#e6e6e2)、変更前の版だけの全体の休みの日は薄い斜線とし、休みがあれば凡例に「全体の休み(変更後)」「変更前だけの休み」を足す。
- 棒は、各版の全体の休みと、そのタスクの作成者の個人の休みの日で切り、続いている日は 1 本にする(プロジェクト計画と同じ)。日数 0 のタスクは、先行が終わった時刻(プロジェクト計画のひし形と同じ位置)を中心に幅 2 px の細い棒を描く。細い棒には縁を付けず、変更前の版は灰の棒と見分けられるよう少し濃い灰(#8a8a86)、変更後の版は黒とする。個人の休みの網は描かない(行が版ごとに分かれ、重ねると読みにくいため)。
- タスクの名前(対応名)が長くて欄に収まらないときは、先頭の側を「…」で縮め、末端の名前と添え書きは残す。
- 対応するタスク(移動を含む)は 1 行に 2 本の棒、増えたタスクは後の版の棒だけ、消えたタスクは前の版の棒だけを描く。増えた・消えたタスクは、タスクの名前の後ろに「(追加)」「(削除)」と書く。
- タスクがどちらの版にもないときは、「タスクがありません」とする(J も同じ)。
- 行の並びは、対応するタスクと増えたタスクを後の版の木の順に並べ、消えたタスクを前の版の木の順に最後に並べる。
- 2 つの版の `end:` に縦線を引く(前の版は点線、後の版は実線)。

**J. 担当者別ガントチャートの比較**

- F の次に置く。
- 担当者の名前の欄の幅の上限は 200 px とし、収まらない名前は先頭の側を「…」で縮める。
- 担当者ごとに 1 行とし、各行を上下 2 段に分けて、上に変更前の版のタスクの棒(薄い灰)、下に変更後の版のタスクの棒(黒枠)を並べる。灰の棒には白い縁を付け、隣り合うタスクが 1 本に見えないようにする。
- 棒にするタスクは、その人が作成者(`by:`)のタスクとする。複数人のタスクは、その全員の行に出す。確認者(`review:`)のタスクは出さない。`by:` のないタスクがどちらかの版にあれば、最後に「(担当なし)」の行を置く(プロジェクト計画の仕様書 7.7 節と同じ)。
- 棒の中には、入る長さのときだけタスクの末端の名前を書く(休みで切れた棒は、いちばん長い切れ目に。日数 0 のタスクの細い棒には書かない)。日数 0 のタスクの細い棒は、隣のタスクの棒に隠れないよう、同じ段のほかの棒の後に描く。棒の位置・目盛り・期限の線・休みは F と同じとする。
- 左に担当者の名前と、作成の日数の「変更前 → 変更後」を置く。
- 行の並びは、変更後の版の `members:` の順とし、変更後にいない人を最後に(変更前の順で)並べる。

### 5.11 タスクの進捗が初めて変わった版

5.9 節の図の下に置く表である。

- 一覧で最後の比べられる版のタスクごとに、隣り合う版の対応(4 章。移動を含む)をさかのぼってたどり、状態が初めて問題発生になった版と、初めて完了になった版を示す。
- 対応が途切れた(名前が変わった)ところより前はたどらない。
- 表の題は「タスクの進捗が初めて変わった版」とし、列は「タスク・問題発生・完了・完了の時期・計画の進捗」とする(問題発生・完了の列は、初めてその状態になった版。計画の進捗の列は、最後の版の `status:`)。
  - 完了の時期は「前の版の日付 〜 初めて完了になった版の日付」とする。初めて完了になった版が、たどった中で最も古い版なら「〜 その版の日付」とする。
  - その状態にならなかったときは「―」とする。
- 行の並びは、最後の版の木の順とする。

### 5.12 図から比べる 2 つの版を選ぶ

- A・D・H の版の位置(点・棒・目盛りの文字)を押すと、その版を後の版、その一つ前の比べられる版を前の版にする。最初の版を押したときは、その版を前の版、次の比べられる版を後の版にする。
- I の列(隣り合う版の組)を押すと、その組を前の版と後の版にする。
- 選んだ 2 つは、利用者が選んだもの(5.2 節)として扱う。表示中のビューは変えない。

### 5.13 改訂履歴(全版)

すべての版の改訂の履歴を、1 つの変更を 1 行にした表で示す。2 つの版の比較ではない。

- 行に入れるのは、比べられる版(3.6 節)だけとし、一覧の順に並べる。各版の行には、その版での改訂、つまり一覧で一つ前の比べられる版からの変化を書く。
- エラーのある版と `version:` のない版は行に入れない。そのような版があれば、表の上に強調の色(えんじ)で警告を出す。
  - 「エラーのため除外: ファイル名、…」
  - 「version: がないため除外: ファイル名、…」
- 列は「版・ファイル・対象・操作・内容」とする。版とファイルは、同じ版の行をまとめたセルにする。内容の列は、ほかの表より広くする(幅の上限 560 px)。
- 変化の種類は「対象」と「操作」の 2 列に分けて書く(表計算ソフトに貼ったとき、対象の列で絞り込めるようにするため)。
- 最初の版の行は、対象を「―」、操作を「初版」、内容を「タスク N 件、終了日 YYYY-MM-DD」とする。
- 2 つ目からの版は、変化ごとに 1 行とし、次の順に並べる。同じ対象と操作の中は、タスクと要素は後の版の木の順(消えたものは前の版の木の順)、メンバーは `members:` の順とする。

| 順 | 対象 | 操作 | 元の節 |
|---|---|---|---|
| 1 | タスク | 追加・削除・移動・変更(この順) | 5.4 節 |
| 2 | タスクの進捗 | 変更 | 5.4 節 |
| 3 | FBS の要素、PBS の要素(この順) | 追加・削除・移動(この順) | 5.6 節 |
| 4 | MOP | 追加・削除・チェック・チェックの取り消し(この順) | 4.6 節 |
| 5 | FBS の根の名前・PBS の根の名前・WBS の根の名前(この順) | 変更 | 4.2 節 |
| 6 | 開始日・期限・全体の休み(この順) | 変更(サマリーの表の値が変わったとき) | 5.1 節 |
| 7 | メンバー | 追加・削除(この順。`members:` のメンバーの増減。タスクへの割り当ての変化は「タスク 変更」に書く) | 5.7 節 |
| 8 | メンバーの休み | 変更(両方の版にいるメンバーの個人の休みが変わったとき) | 5.7 節 |
| 9 | 終了日 | 変更(担当を入れた日程の終了日が変わったとき) | 5.5 節 |

- 内容の書き方は、対象と操作ごとに次のとおりとする。メンバーの追加・削除はメンバーの名前とする。
  - タスク・要素の追加・削除・移動: 対応名。移動は「対応名(親: 前の親 → 後の親)」。子要素ができた・なくなったときの添え書きは 5.4 節と同じ。
  - タスク 変更: 「対応名(項目 変更前 → 変更後、…)」。項目は 5.4 節の変わったタスクの項目(状態を除く)。作成者・確認者・対象・先行のように値が複数あるときは、値を「・」でつなぐ(項目の区切りの「、」と見分けるため。ほかの表も同じ)。
  - タスクの進捗 変更: 「対応名(変更前 → 変更後)」。
  - FBS の要素 追加・削除: 対応名に、その要素の MOP を「(MOP: 文 / 文)」と添える(機能とテストがいつ足されたかを見られるようにするため)。MOP がなければ添えない。
  - MOP の各操作: 「FBS の要素の対応名: MOP の文」。
  - 根の名前 変更: 「変更前の名前 → 変更後の名前」。
  - 開始日・期限・全体の休み 変更: 「変更前 → 変更後」。期限と全体の休みがないときは「なし」と書く。全体の休みは注を除いた書いたままの文とする。
  - メンバーの休み 変更: 「名前(変更前 → 変更後)」。値の書き方は 5.7 節と同じ。
  - 終了日 変更: 「YYYY-MM-DD → YYYY-MM-DD(差の暦日)」。
- 全体の休みとメンバーの休みは、5.7 節と同じく、空白や並びだけの違いを変更としない。
- 前の版から何も変わっていない版(注や空白だけが違う版)は、対象を「―」、操作を「変更なし」とする 1 行を置く。
- 行を押すと、その版を後の版、一覧で一つ前の比べられる版を前の版にする(5.12 節と同じ。最初の版の行は、その版と次の版)。
- 表なので、題の右の「コピー」でコピーできる(8.2 節)。

## 6 章 作業分析

マイログと計画書を突き合わせる。マイログの一覧が空のときは、作業分析のビューを出さない(8.1 節)。

### 6.1 メンバー

- メンバーは、マイログの一覧の `by:` の名前と、基準日の版の `members:` のメンバーを合わせたものとする。
- 並びは、基準日の版の `members:` の順、続いて `members:` にいない `by:` をマイログの一覧の順とする。
- `members:` にいてマイログのない人は、要確認(S1)に「マイログがありません」と出す。エラーのあるマイログしかない人は、ここに入れない(3.7 節)。

### 6.2 基準日と基準日の版

- 基準日は、画面の基準日の欄で決める。既定は表示する日の日付(今日)とする。
- 進捗の管理(TA・メンバー)では今日のまま使い、提出物の確認(教員)では締め切りの日などを入れて使う。
- 基準日は、ページを開き直すと今日に戻る(自動保持に残さない)。
- 基準日の版は、計画書の一覧の比べられる版(3.6 節)のうち、版の日付が基準日以前のもので、一覧でいちばん後ろの版とする。基準日以前の版がなければ、一覧でいちばん前の版とする(マイログの仕様書 5.4 節と同じ)。基準日を過去の日にすると、記録と同じく計画書も、その日の時点のもので兆候・集計・反映候補を出す。
- 基準日が今日のまま表示したまま日付が変わったら描き直す(プロジェクト計画のガントチャートと同じ)。
- 計画書分析(5 章)は、基準日を使わない。

### 6.3 兆候

兆候は、規則と、それに当たった記録の行だけを示す。良し悪しの判断や解釈の文は出さない。S1・S2・S4〜S9 の規則はマイログの仕様書 6.2 節と同じとし、メンバー全員について判定する。

| 番号 | 兆候 | 規則(マイログとの違い) | 既定の値 |
|---|---|---|---|
| S1 | 記録の途絶 | メンバーごとに判定する。マイログのない人も含める。エラーのあるマイログしかない人は含めない(3.7 節) | 7 日 |
| S2 | 問題の長期化 | `issue:` は、どのメンバーの `solved:` でも閉じる(同じ記録先か同じ名前。マイログの仕様書 4.3 節)。同じ日付なら、別の人のマイログの `solved:` は、一覧の順によらず後とみなす。`blocked` は、人ごとの最後の報告でまとめた状態(マイログの仕様書 4.2 節・4.3 節)が問題発生でなくなるか、どのメンバーの `solved:` でも閉じる。閉じ方は一覧の順によらない | 7 日 |
| S3 | 返事待ち | 依頼(`review:`・`ask:`)から、相手の対応(6.5 節)がないまま N 日以上たっている(作業分析だけの兆候) | 3 日 |
| S4 | 日数の超過 | 作業日数(`hours:` を書いた日の数)は、全員の記録の日付を合わせて数える(同じ日は 1 日) | ― |
| S5 | 終了予定日の超過 | 今の状態は、人ごとの最後の報告でまとめたもの(マイログの仕様書 4.2 節) | 1 日 |
| S6 | 手戻り | 日ごとに、その日までの人ごとの最後の報告でまとめた状態で判定する | ― |
| S7 | 計画にない作業 | メンバーごとに判定する。週は 6.6 節の週とする | 50 % |
| S8 | 進捗の停止 | 進捗率は、人ごとの最後の進捗率の平均(マイログの仕様書 4.2 節)で判定する。基準日の版のタスク(3.8 節で寄せた記録先)と、計画にない作業の記録先だけを見る | 14 日 |
| S9 | 確認の抜け | 完了の報告と `review:` は、誰の記録でもよい | ― |

- 規則の値(N)は、設定のダイアログで変えられる。変えた値は自動保持に残す(plans には書かない)。
- 計画書が要る兆候(S1・S4・S5・S7・S9)は、計画書の一覧が空のとき判定しない(マイログの仕様書 6.2 節と同じ)。

### 6.4 要確認の表

- 列は「兆候・人・記録先・内容・日付」とする。人は、S1・S7 ではそのメンバー、S2・S3・S6 では記録者(S3 は「依頼した人 → 相手」)、それ以外は基準日の版の作成者(`by:`)とする。計画にない作業の記録先に出る S8 は作成者がいないので、記録者とする。
- 行の並びは、兆候の番号の順、同じ兆候の中はメンバーの順(6.1 節)とする。S3 は依頼した人、作成者が 2 人以上のときは最初の人の順とする。
- 表の上に、基準日と規則の値を書く。
- 先頭に、3.7 節の注意(同じ人のマイログが 2 つ、エラーのため除外)と 6.6 節の注意(`week:` がそろっていない)を強調の色(えんじ)で出す。

### 6.5 依頼の突き合わせ

**対応の決め方**

- 依頼は、マイログの `review:`(確認)と `ask:`(質問)である。依頼した人・相手・記録先・日付・種類を持つ。相手が複数なら、相手ごとに 1 つの依頼とする。
- 相手のマイログに、同じ記録先か同じ名前(書いたままの名前)で、依頼の日付以降(同じ日を含む)の返事(確認は `reviewed:`、質問は `answered:`)があれば、対応済みとする。返事の日付は、その記録の日付とする。
- 1 つの返事は、それより前の、同じ相手・同じ種類で、同じ記録先か同じ名前の未対応の依頼をすべて対応済みにする。
- 記録先は、基準日の版に寄せた記録先(3.8 節)で比べる。移動をまたいだ依頼と返事も対応する。名前の変更をまたいだときは、同じ名前で書いた返事だけが対応する。
- 相手のマイログが一覧にないときは、未対応とし、内容に「相手のマイログがありません」と添える。相手のマイログがエラーで集計から外れているときは「相手のマイログにエラーがあり、集計から外しています」と添える。

**受けた依頼の表**

- メンバーごとに 1 行とし、列を「人・受けた依頼・対応済み・未対応・最長の返事待ち(日)・差し戻し」とする。差し戻しは、その人が書いた `reviewed: ng` の件数とする。
- 数を並べるだけで、良し悪しは書かない。

**依頼の一覧**

- 依頼ごとに 1 行とし、列を「日付・依頼した人・相手・種類・記録先・返事の日・結果・状態」とする。結果は `ok`・`ng`・`answered:` の値(要旨)、状態は「対応済み」か「未対応(N 日)」とする。
- 行の並びは、依頼の日付の順とする。

### 6.6 集計の決まり

- 週の始まりの曜日は、集計に使うマイログ(エラーで外したものを除く)の `week:` がすべて同じなら、その曜日とする。違うとき、マイログがないときは `mon` とし、違うときは要確認の先頭に「マイログの week: がそろっていません(名前: 曜日、…)。月曜から区切ります」と出す。
- 週の列は、最初の記録の週から、基準日の週までとする。
- 列の見出しは週の始まりの日付(「MM-DD〜」)とする。
- 表の「タスク」「記録先」「機能」の列には、対応名を書く(列名には「(対応名)」を付けない)。
- 表の数は、基準日より後の記録を含めない。
- 同じ日付の中の行の並びと、記録者を並べる順は、メンバーの順(6.1 節)とする。マイログの一覧の順にはよらない。

### 6.7 作業時間(人×週)

- 行をメンバー、列を週とし、`hours:` の合計を書く。最後の列に合計時間、最後の行に週ごとの合計を置く。記録のない週は 0 と書く(作業していないことが見えるように)。
- 表の下に、メンバーごとの週の合計時間の折れ線の図を置く。線はすべて黒とし、線の右端に名前を書く(5.9 節の H と同じ)。

### 6.8 作業時間(タスク×週)

- 行を記録先(計画にない作業を含む)、列を週とし、全員の `hours:` の合計を書く。計画にない作業は、名前の後ろに「(計画にない作業)」と書く(計画から削除した記録先は「(計画から削除)」。マイログの仕様書 5.6 節)。
- 列は「WBS 番号・記録先・週ごとの時間…・合計時間・計画の日数・作業日数」とする。
  - WBS 番号: 基準日の版の WBS の管理番号(途中の要素にも振られている)。FBS の機能、計画にない作業、基準日の版にない記録先は「―」とする。
  - 計画の日数: 基準日の版の `days:`。WBS の末端のタスクだけに書き、ほかは「―」とする。
  - 作業日数: `hours:` を書いた日の数。全員の記録の日付を合わせて数える(同じ日は 1 日。6.3 節の S4 と同じ数え方)。計画の日数と並べ、計画とどれだけ違ったかを見るための列である。
- 行の並びは、基準日の版の WBS の木の順、続いて FBS の木の順、最後に計画にない作業を最初に書かれた順とする(マイログの仕様書 7.3 節の担当外の記録と同じ)。

### 6.9 進捗

- 表とし、図(ガントチャート)は描かない。日程の図はプロジェクト計画で見る。
- 基準日の版のタスクごとに 1 行とし、列を「WBS 番号・タスク・作成者(計画)・予定の期間・始めた日・完了した日・区分・最後の進捗・最後の進捗率・報告日・記録者・計画の進捗」とする。WBS 番号は WBS の管理番号とする。
- 行の並びは、基準日の版の WBS の木の順とする(プロジェクト計画の WBS と見比べやすくするため)。
- 区分は、マイログの仕様書 7.1 節の区分(遅延・問題発生・開始予定日を過ぎた未着手・実行中・開始予定日がまだ先・完了。この順に判定して 1 つに決める)を、全員の報告から決めた今の状態と基準日で判定したものとする。遅延は「遅延(N 日)」と、終了予定日から基準日までの日数を添える。まだ始めていないだけのタスク(開始予定日がまだ先)と、対応が遅れているタスク(遅延・開始予定日を過ぎた未着手)を見分けるための列である。
- 始めた日・確認待ちは、マイログの仕様書 7.1 節と同じ決め方とし、全員の記録から決める。確認待ちは、依頼した相手の全員が、依頼の日以降にそのタスクに確認の結果(`reviewed:`)を書いていれば終わる。
- 完了した日: 最後の状態が完了のとき、その完了の報告の日付とする。最後の状態が完了でなければ「―」とする(完了と報告した後に実行中などに戻したタスクは、完了した日を書かない)。確認待ちのタスクは、最後の状態の後ろに「(確認待ち)」と添える。
- 最後の状態と最後の進捗率は、人ごとの最後の報告でまとめたもの(マイログの仕様書 4.2 節。基準日の版の作成者の誰かが報告していれば作成者の報告だけでまとめる。状態は全員が完了なら完了・1 人でも問題発生なら問題発生・それ以外で誰かが着手していれば実行中、進捗率は平均)とする。報告日と記録者は、まとめに使った報告のうち、いちばん新しい報告のものとする。報告がなければ「―」とする。
- 最後の進捗の列は、状態の色で塗る(プロジェクト計画と同じ)。
- 進捗率の小計(途中の要素やプロジェクト全体の平均など)は出さない(1.2 節)。

### 6.10 TRL・TPM

- TRL の推移: 行を機能(記録先)、列を週(6.6 節の週の列。作業時間と同じく、最初の記録の週から)とし、その週の最後の報告の値を書く。表の下に、機能ごとの折れ線の図を置く(線は黒、右端に名前)。
- TPM の推移: TRL と同じ形の表に、書いたままの文を書く。図は描かない(値が文のため)。

### 6.11 テストの記録

- テスト(`test:`)ごとに 1 行とし、列を「新/再・機能・MOP・実施日・結果・記録者・メモ」とする(講義資料のテストの実施日と結果の表の形)。
- 同じ機能・同じ MOP の文の最初のテストを「新」、2 回目からを「再」とする(誰のマイログに書かれたかによらない)。
- 行の並びは、実施日の順とする。

### 6.12 メンバーごとの負荷

作業負担の分散を検討するための表である(講義の「作業負担の分散を検討」)。

- メンバーごとに 1 行とし、並びは 6.1 節のメンバーの順とする。
- 列は「メンバー・未完了のタスク・計画の日数・遅延・問題発生・先週の時間・今週の時間」とする。
  - 未完了のタスク: 基準日の版で `by:` にそのメンバーがいて、区分(6.9 節)が完了でないタスクの件数。
  - 計画の日数: それらのタスクの `days:` の合計。作成者が 2 人以上のタスクは、それぞれのメンバーに全部の日数を数える(分け方は計画に書かれていないため)。
  - 遅延・問題発生: それらのタスクのうち、区分が遅延・問題発生のものの件数。
  - 今週の時間・先週の時間: 基準日を含む週(6.6 節の週)と、その前の週の `hours:` の合計。
- 数を並べるだけで、良し悪しは書かない。

### 6.13 影響を受けるタスク

遅れているタスクの後ろにつながるタスクを示す表である。どのタスクを前にするか・後ろにするかを考える材料にする。計画の日程は変えない(日程を変えるのはプロジェクト計画で行う)。

- 区分(6.9 節)が遅延・問題発生・開始予定日を過ぎた未着手のタスク(遅れているタスク)ごとに、その後続のタスク(影響を受けるタスク)を並べる。
- 後続のタスクは、基準日の版の `after:`(プロジェクト計画の仕様書 4.4 節の決まり。途中の要素を指す `after:`、途中の要素に書いた `after:` を含む)をたどって、遅れているタスクの後に始まる必要があるタスクとする。直接つながるもの(直接)と、それより先につながるもの(間接)の両方を入れ、区分が完了のものは入れない。完了のタスクの先はたどり、その先の完了していないタスクは間接として入れる。
- 列は「遅れているタスク(WBS 番号・対応名)・遅れているタスクの区分・影響を受けるタスク(WBS 番号・対応名)・つながり(直接・間接)・その作成者・その開始予定日・影響を受けるタスクの区分」とする。「その」は影響を受けるタスクを指す。
- 行の並びは、遅れているタスクの WBS の木の順、その中は影響を受けるタスクの開始予定日の順とする。
- 遅れているタスクがなければ「遅れているタスクはありません」、影響を受けるタスクがなければその遅れているタスクの行に「影響を受けるタスクはありません」と書く。

### 6.14 チームの週のまとめ

選んだ 1 週間のチーム全員の記録を 1 枚にまとめる(講義の進捗報告と議事録のもと)。マイログの週のまとめ(マイログの仕様書 7.7 節)のチーム版である。

- 週は、ビューの上の帯の選択欄で選ぶ。選べる週と既定は、マイログの仕様書 7.7 節と同じとする(最初の記録の週から基準日の週まで。日付の行だけの日も記録に含める。既定は基準日の週。新しい順)。マイログの一覧が変わって、選んでいた週が選べなくなったときは、基準日の週に戻す。週の始まりは 6.6 節のとおり。選んだ週は保存しない。印刷では基準日の週を出す。
- 題は「週のまとめ(YYYY-MM-DD〜YYYY-MM-DD)」とし、その下に、メンバーごとの記録日数と合計時間の表(列は「メンバー・記録日数・合計時間」。マイログのない人も 0 で入れる)を置く。
- 続いて次の表を置く。列はマイログの週のまとめの表に記録者の列を足したものとする。どれも、該当がなければ「なし」とする。
  1. この週に完了したタスク: 完了の報告(`status: done`)がこの週にあるタスク。列は「日付・記録者・タスク(番号・対応名)」。
  2. この週の作業時間: 記録先ごとの時間と、記録者。
  3. この週の問題と解決
  4. この週の依頼と返事(依頼には、6.5 節の対応の状態を添える)
  5. この週のメモ(日付の行のメモの行も、押すとそのマイログの行を示す)
  6. この週のテスト・TRL・TPM

### 6.15 MOP の達成状況

すべての MOP について、テストで確かめられたかを示す表である。

- 基準日の版の FBS の機能ごとに、その MOP を 1 行ずつ並べる。並びは FBS の木の順、同じ機能の中は MOP を書いた順とする。
- 列は「機能・MOP・計画・最後のテスト・最後のテストの日・記録者・テストした回数」とする。
  - 計画: 計画でチェック済み(`mop*:`)なら「✓」。
  - 最後のテスト: 全員の記録のうち、その機能に書いた `test:` で `mop:` の文がその MOP と一致する最後のものの結果(ok・ng)。なければ「未実施」。
- 表の上に「MOP 全 N 件: ok A 件、ng B 件、未実施 C 件」と数を書く。
- 6.16 節の反映候補(計画に書き写すもの)と違い、未実施を含むすべての MOP を出す。

### 6.16 計画への反映候補

基準日の版と、全員の記録を比べ、計画に書き写す候補を示す。アプリは計画を書き換えない。

| 候補 | 条件 |
|---|---|
| 進捗の変更 | タスクの最後の状態が、基準日の版の `status:`(なければ実行前)と違う |
| MOP のチェック | MOP の最後のテストの結果が `ok` で、基準日の版で `mop:`(チェックしていない)のもの |
| MOP のチェックの取り消し | MOP の最後のテストの結果が `ng` で、基準日の版で `mop*:`(チェック済み)のもの |
| 計画にない作業 | 計画にない作業に `hours:` が書かれている(計画に足すかどうかを考える材料)。計画から削除した記録先(マイログの仕様書 5.6 節)は出さない |

- 計画書の一覧が空のときは、「計画書を読み込むと候補を示します」とする。

  - フッター

### 8.2 表のコピーと保存

- 各表の題の右に「コピー」「SVG」「PNG」「PDF」のボタンをこの順に置く。「SVG」「PNG」は、その表を 1 つずつ画像で保存し、「PDF」はその表だけを同じ大きさの紙で印刷する(9.3 節・9.4 節)。
- 「コピー」は題の文字のすぐ右に置き(題の文字のすぐ右に置き、ボタンの文字と題の文字の見た目の中心をそろえる。中心は、フォントによって変わる上下の余白ではなく、文字の基準線から求める)、表をタブ区切りの文字でクリップボードに写す。ボタンは図の上に重ねて置く画面の部品とし、SVG には含めない(保存した画像や印刷には出ない)。画面の上の帯には置かない。

- 行の区切りは LF とする。セルの値にタブや改行が含まれるときは、空白 1 個に置き換える。
- 写したら「コピーしました」を 2 秒出し、元の文に戻す。続けて押したときも、元の文に戻す。写せなかったときは、その旨を出す。
- CSV のファイルの保存は設けない。
- コピーの対象は、画面に表として描いた表だけとする。5.5 節・5.9 節・5.10 節の図の元の数はコピーの対象にしない。

## 9 章 保存と読み込み

### 9.1 plans の形式

- JSON とし、文字コードは UTF-8(BOM なし)、改行は LF とする。拡張子は `.plans`。
- 中身は、計画書の一覧の順に並べた各版のファイル名とテキスト(`files`)と、マイログの一覧の順に並べた各マイログのファイル名とテキスト(`logs`)である。並びが手で並べ替えた順を兼ねる。
- マイログの一覧が空のときは、`logs` を書かない(マイログを使わないときは、これまでの plans と同じファイルになる)。
- `logs` のない plans も読む(マイログの一覧には何も足さない)。
- `version:` は持たない。
- 比べる 2 つの版の選択、ビュー、基準日、規則の値など、見ている状態は入れない。
- 形は次のとおりとする。キーの順と字下げ(空白 2 個)を固定し、同じ一覧からは同じファイルを書く。

```
{
  "format": "projalysis-plans",
  "files": [
    {
      "name": "team_a.plan",
      "text": "version: 2026-04-20\nstart: 2026-04-23\n..."
    },
    {
      "name": "team_a_2.plan",
      "text": "..."
    }
  ],
  "logs": [
    {
      "name": "青木.mylog",
      "text": "version: 2026-04-29\nby: 青木\n..."
    },
    {
      "name": "井上.mylog",
      "text": "..."
    }
  ]
}
```

- `format` が違う、または形が合わないファイルは、読めないことを知らせて読まない。
- エラーのある版とマイログも plans に入れる。
- `format` を変えず、`logs` を足しただけなので、`logs` を知らない版のプロジェクト分析と、マイログ(計画書だけを読む。マイログの仕様書 9 章)も、この plans の計画書を読める。

### 9.2 上書き保存・別名で保存

プロジェクト計画の仕様書 9 章の上書き保存・別名で保存に合わせる。違う点は次のとおり。

- 保存するのは plans である。名前の候補は今のファイル名、なければ「計画書の一覧の最初の版のファイル名から拡張子を除いたもの.plans」、計画書の一覧が空なら `projalysis.plans` とする。
- 上書きの先は、開いた `.plans` とする。`.plan`・`.mylog` から始めた一覧と、プロジェクト計画の SVG から始めた一覧には上書きの先がなく、上書き保存では保存先を尋ねる。ファイル操作機能のないブラウザでは、ファイル名があれば同じ名前でダウンロードする(プロジェクト計画と同じ)。上書きに失敗したときは知らせるだけとし、別名で保存には進まない。Ctrl+Shift+S では保存しない。
- 足す・外す・置き換える・並べ替えは、どちらの一覧でも保存していない変更とし、ファイル名の後ろに ` *` を付ける。
- 「新規」は 2 つの一覧を空にする。保存していない変更があれば、空にしてよいかを確かめる。上の帯の読み込みの警告(読めなかったファイル)も消す。例を読み込んだときも同じ。
- 書き込むテキストは、改行を LF とし、BOM を付けない。
- 書き込みの間は、上書き保存・別名で保存のボタンと Ctrl+S を受け付けない(2 回書き込まない)。書き込みの間に一覧が変わったら、書き込んだ後も ` *` を残し、「保存中に変わった内容はまだ保存されていません」と添える。書き込みの間に別の plans を開いた(新規・例を含む)ときは、ファイル名と上書きの先を、開いた plans のままにする。

### 9.3 SVG

- 図のあるビュー(推移・日程・ガントチャート・作業時間(人)・TRL・TPM)では、各図の題の右に「SVG」「PNG」「PDF」のボタンを置き、図を 1 つずつ保存できる(PDF は 9.4 節)(ボタンは 8.2 節の「コピー」と同じく図に含めない)。保存する図には図の題を付ける(F・J・G には変更前と変更後の版、G には 5.5 節の 3 つの数も付ける)。ファイル名は「元の名前_ビューの識別子_図の識別子」とする(例: `team_a_trend_status.svg`)。
- 表は、各表の題の右の「SVG」「PNG」「PDF」で 1 つずつ保存できる(8.2 節。PDF は 9.4 節)。保存する表には題を入れない(報告書では題を表の上に書くため)。ファイル名は「元の名前_ビューの識別子_表の題」とする。表の題は件数を除いたものとし、ファイル名に使えない文字と空白は「_」にする(例: `team_a_tasks_追加したタスク.svg`)。
- 元の名前は、今のファイル名、なければ計画書の一覧の最初の版のファイル名から拡張子を除いたもの、それもなければ `projalysis` とする。元の名前も、ファイル名に使えない文字と空白は「_」にする。
- ファイル名の形「元の名前_ビューの識別子_図の識別子か表の題」は、プロジェクト計画・マイログと同じとする(プロジェクト計画の仕様書 9 章)。ビューの識別子は、サマリー `overview`、計画への反映候補 `reflect`、要確認 `alerts`、週のまとめ `week`、依頼 `requests`、負荷 `load`、進捗 `progress`、影響を受けるタスク `impact`、作業時間(人) `hoursPeople`、作業時間(タスク) `hoursTasks`、TRL・TPM `trl`、テストの記録 `tests`、MOP の達成状況 `mop`、改訂履歴 `history`、推移 `trend`、WBS `tasks`、日程 `sched`、FBS・PBS・MOP `fbs`、メンバー `people`、ガントチャート `gantt` とする。作業分析の図の識別子は、作業時間(人)の折れ線の図 `people`、TRL の折れ線の図 `trl` とする。
- 保存する SVG には、読み込んだ版を埋め込まない(正本は plans だけとする)。そのため、保存した SVG をプロジェクト分析で開いても版は戻らない。
- 表示中のビュー全体を 1 枚の画像で保存することはしない(図と表を 1 つずつ保存するか、印刷 / PDF を使う)。
- 5 章の図の記号(A〜J)は、この仕様書の中で図を指すためだけに使い、画面の題・保存する図・ファイル名には出さない。画面の題と識別子は次のとおりとする。

| 記号 | 画面の題 | 識別子 |
|---|---|---|
| A | 終了日の推移 | `end` |
| E | バーンアップ(横軸は版の日付) | `burnup` |
| D | タスク数と進捗の推移 | `status` |
| I | 変更の多い部分(WBS の第 1 層ごとのタスクの変更数) | `changes` |
| H | 担当者ごとの作成の日数 | `effort` |
| F | ガントチャートの比較 | `gantt` |
| J | 担当者別ガントチャートの比較 | `gantt-people` |
| G | 見積もりの変化 | `estimate` |

### 9.4 PNG・PDF

- 図と表を 1 つずつ PNG で保存できる(9.3 節と同じく、題の右の「PNG」)。中身とファイル名の形は SVG と同じとし、解像度は 2 倍とする。
- 題の右の「PDF」は、その図または表だけを、それと同じ大きさの紙(余白 0)で印刷する。印刷の画面で「PDF に保存」を選ぶと、余白のないベクター形式の PDF 1 ページになる(TeX などにそのまま貼れる)。中身は SVG と同じとする。印刷の画面のファイル名の候補は、SVG と同じ形(拡張子なし)とする。アプリの中で PDF のファイルを作ることはしない。
- 印刷の領域に入れる図(全体の印刷と「PDF」)は、属性の `id` と `url(#…)` に印を付け(タスクの名前などの文の中に書いた `url(#…)` は変えない)、画面の図と重ならないようにする(重なると、印刷では見えない画面の側の模様を指し、斜線などが消えるため。プロジェクト計画と同じ)。全体の印刷の前には、「PDF」の紙の指定が残っていれば戻す。
- 保存する SVG にも、同じ紙の大きさの指定(`@page`)を入れる。保存した SVG をブラウザで開いて印刷しても、同じ大きさの PDF になる。
- 紙の大きさの指定は Chrome・Edge で確かめている。Safari では効かないことがある。

### 9.5 印刷 / PDF

- ビューをすべて、8.1 節の順に、1 つ以上のページに印刷する。マイログの一覧が空なら、作業分析のビューは印刷しない。比べられる版が 2 つ未満なら、2 つの版を比べるビューは印刷しない。すべての版を示すビュー(推移・改訂履歴)とサマリーは、比べられる版が 1 つでも印刷する。
- 週のまとめは、基準日の週を印刷する。基準日で変わる表(作業分析と作業の概要)は、表の上の文に基準日が入る。
- ページの向きは、サマリーと計画書分析は横、作業分析は縦とする(作業分析の表はチームログと同じく縦のページに合わせて区切るため)。紙は A4 とする。作業分析の図のうち、縦の紙で元の大きさの半分より小さくなる幅のもの(週の多い折れ線の図など)は、横のページにする。
- A4 横の 1 ページに収めると元の大きさの半分より小さくなる表は、ページを分ける(判定はプロジェクト計画の仕様書 9 章と同じ)。
  - 5.4 節〜5.7 節の表は、行で区切り、各ページに見出しを付ける。まとめたセルはページの境目で切って描く。比較の要約は最初のページにだけ置く。
  - 表の題は、表の見出しの行と最初の行と同じページに置く。1 行だけでページに収まらない行は、その行を区切らずに置き(半分より小さく縮むことがある)、題だけのページは作らない。
  - サマリーの表は列(版)で区切り、各ページの左に行の見出しの列を置く。作業の概要は最初のページにだけ置く。
  - 作業分析の表は行で区切る。縦の紙で元の大きさの半分より小さくなる幅の表は、先頭の列(作業時間(タスク×週)は WBS 番号と記録先、ほかは最初の列)を各ページに残して、列でも区切る。題には「(列 1/3)」のように区切った位置を添える。
  - 推移のビューは、図 1 つと 5.11 節の表を、それぞれ別のページにする。版が多くて図が半分より小さくなるときは、横軸の版で区切ってページを分ける。5.11 節の表は行で区切る。
  - 日程のビューは、G の題より前を表と同じく行で区切り、G を別のページにして行で区切る(続きのページの題は「見積もりの変化(続き)」)。G の最初のページには「比較: … → …」を置く。
  - ガントチャートのビューは、比較の要約を独立したページにし、F・J をそれぞれ別のページにして行で区切る。F・J の最初のページは、「比較: … → …」と図の題と図だけとする(PDF から図だけを切り出しやすくするため)。
- 各ページには表だけを置き、ファイル名や日付などの文字は足さない。ページの余白は 0 とし、表の周りの空き(10 mm)はページの内側に取る(プロジェクト計画と同じ)。

### 9.6 自動保持

- 計画書の一覧とマイログの一覧(各ファイルのファイル名とテキスト、並び)・ファイル名・保存していない変更があるか・比べる 2 つの版と、それを利用者が選んだか(5.2 節)・表示中のビュー・6.3 節の規則の値・一覧の折りたたみを、変わるたびに、このブラウザの `localStorage` に保持する。どこにも送信しない。基準日と、週のまとめで選んだ週は保持しない。
- 開いたときは、保持してある内容を続きとして開く。一覧は 3.4 節の順に並べ直す(同じ日付の中は保持した順のまま)。なければ空で開く。規則の値は、0 以上の数だけを戻す(ほかは既定の値)。
- ページを開き直すと上書きの先は忘れ、次の上書き保存では保存先を尋ねる(プロジェクト計画と同じ)。
- 保持に失敗したとき(容量超過など)は、上の帯に警告を出す。一覧が空のときは出さない。
- 別のタブで同じ一覧が変わったときは、上の帯に警告を出す。
