# プロジェクト分析(projalysis.sapp.jp)仕様書

版 0.31(2026-10-27)

この文書は、アプリの外から見た仕様(読み込み、対応づけ、比べる内容、ビュー、画面、保存)を定める。実装の作り方は、計算部の取り込み(9 章)を除いて定めない。実装は index.html(単一 HTML)で、この仕様書に沿って作る。

本文中の【提案】は、まだ承認を得ていない部分である。一覧は 10 章にまとめる。【提案】の付いていない部分は、確定した決定事項である。

## 1 章 目的と範囲

### 1.1 目的

プロジェクト計画(plan.sapp.jp)で書いた複数の `.plan` を読み、変更箇所と変更履歴を決まった形の表と図で出す。

- 版を `version:` の日付の順に並べ、変更履歴を追えるようにする。
- 選んだ 2 つの版の間で、何が増え、何が消え、何が変わったかを示す。
- 書式が人によって変わらないので、比べた結果を読む側(採点者など)の手間が減る。
- 計画が版を追ってどう変わったか(延び・範囲・進み・計画が不安定だった部分・負担の偏り)を図で示し、作った人(学生・PM)自身が振り返れるようにする。

### 1.2 範囲

- `.plan` を読んで比べるだけで、編集はしない。テキスト欄を持たない。
- `.plan` の解析と日程の計算は、プロジェクト計画と同じ計算部で行う(3.2 節)。記法の規則はプロジェクト計画の仕様書による。
- 要素は名前で対応づける(4 章)。名前の似た要素を推測して対応づけることはしない。
- `.plan` には実績の日付がない。日程の比較は、各版のテキストから計算した予定どうしの比較である。
- 実績の日付と工数は扱わない(プロジェクト計画にも入れない)。変化は版の単位でとらえ、「どの版から変わったか」を示す。あるタスクが初めて完了になった版から、完了の時期をその版と前の版の日付の間に絞れる(5.11 節)。
- 使う人と使い方は定めない。

### 1.3 S Apps としての前提

- 単一 HTML で、サーバーにデータを送らず、ネットなしで動く。
- 外部ライブラリを読み込まない。
- アプリ本体に Node.js を含めない。ビルドと検査に使うのはよい。
- 同じファイルの並びからは、必ず同じ表と図を出す(決定的)。表示する日の日付には依存しない。
- ライセンスは MIT とする。

### 1.4 名前

- アプリ名(上の帯・タブの題名): プロジェクト分析
- 公開先: projalysis.sapp.jp
- リポジトリ名: projalysis

## 2 章 用語

プロジェクト計画の仕様書 2 章の用語(節・根・要素・末端・途中の要素・タスク・属性・エラー・警告など)は、そのまま使う。

画面では、下の表の「増えた」「消えた」「変わった」「前の版」「後の版」「状態」を、それぞれ「追加」「削除」「変更」「変更前」「変更後」「進捗」と表記し、「終わりの日」は「終了日」と表記する。画面の文言は簡潔にする。人については、チームにいる人そのもの(`members:` の並び・メンバーの増減・個人の休み)を「メンバー」、タスクに割り当てられた人(作成者・確認者・担当者ごとの作成の日数・担当なし)を「担当者」と表記する。

| 用語 | 意味 |
|---|---|
| 版 | 読み込んだ `.plan` 1 つ |
| 版の日付 | その `.plan` の 1 行目の `version:` の日付 |
| 版の名前 | 画面と表で版を示す名前(3.5 節)。例: 「2026-10-27 版」「2026-10-27 版 (2)」 |
| 一覧 | 読み込んだ版の並び(3.4 節) |
| plans | 一覧をまとめて保存するファイル(7.1 節)。拡張子は `.plans` |
| 比べられる版 | エラーがなく、版の日付がある版(3.6 節) |
| 前の版・後の版 | 比べる 2 つの版のうち、一覧で前にあるものと後ろにあるもの(5.2 節) |
| 対応名 | 対応づけに使う名前。根を除いた祖先と自分の名前を `::` でつないだもの(4.1 節) |
| 対応する | 前の版と後の版で、同じ要素とみなすこと(4 章) |
| 増えた | 後の版にだけある |
| 消えた | 前の版にだけある |
| 移動 | 名前が同じで、親が変わった(4.3 節) |
| 変わった | 対応するタスクの属性の値が違う(5.4 節) |
| 隣り合う版 | 比べられる版だけを一覧の順に並べたとき、隣り合う 2 つの版 |
| 第 1 層の要素 | WBS の根の子。工程(フェーズ)とは限らない |
| 進捗 | タスクの `status:` の値(実行前・実行中・完了・問題発生)。画面での「状態」の表記 |

## 3 章 読み込み

### 3.1 読めるファイル

- `.plan`: プロジェクト計画のテキスト。
- `.plans`: プロジェクト分析で保存した plans(7.1 節)。
- プロジェクト計画の版 0.30 までに「画像…」で保存した SVG(テキストを埋め込んだもの)も、埋め込まれた `.plan` を 1 つの版として読む。ファイル名は「SVG の名前.plan」とする。プロジェクト計画の版 0.31 以降で保存した SVG にはテキストが入っていないので読めない。読めないときは「この SVG には .plan が埋め込まれていません(開ける .svg は、プロジェクト計画の版 0.30 までに「画像…」で保存したものだけです)」と知らせる。【提案】
- 文字コードは UTF-8 とする。BOM があれば除く。改行は LF と CRLF のどちらも読む。
- 開けない拡張子のファイルは、開けないことを知らせて読まない。

### 3.2 計算部

- `.plan` は、プロジェクト計画の計算部(core.js の `/*CORE-BEGIN*/` 〜 `/*CORE-END*/`)の `analyze` で読む。
- 読み込むすべての版を、同じ版の計算部で読む。
- 計算部の版を画面には書かない。

### 3.3 足す

- 開く(ファイル選択で複数選べる)・ファイルを置く(複数をまとめて置ける)は、どちらも一覧に足す。一覧を入れ替えることはしない。
- `.plans` を足したときは、その中の `.plan` をすべて足す。
- テキストが一覧のどれかと 1 文字も違わない `.plan` は足さず、「同じ内容のため追加しませんでした: ファイル名(同じ内容のファイル名 と同じ)」と知らせる(例: 「b.plan(a.plan と同じ)」)。`version:` の日付だけが違うものは、別の版として足す。
- ファイル名が同じでテキストが違う `.plan` は、別の版として足す。
- 一覧の各版には外すボタンを付け、押すと一覧から除く。

### 3.4 一覧の並び

- 版の日付の古い順に並べる。
- 同じ日付の版の中の並びは、次のとおりとする。
  - 先に一覧にあった版を前、後から足した版を後ろにする。
  - 一度に複数を足したときは、足した順(ファイル選択や置いたときに渡された順、plans の中の順)とする。
  - 同じ日付の版の中だけ、手で並べ替えられる。日付をまたいで動かすことはできない。並べ替えるボタンは、各版に付けた上へ(▲)・下へ(▼)とする。【提案】
- 手で並べ替えた順は、plans・自動保持に残す。
- 版の日付のない版(3.6 節)は、一覧の最後に、足した順に並べる。【提案】

### 3.5 版の名前

- 「YYYY-MM-DD 版」とする。
- 同じ日付の版が 2 つ以上あるときは、一覧の並びの順に 2 つ目から「YYYY-MM-DD 版 (2)」「YYYY-MM-DD 版 (3)」…とする。1 つ目には番号を付けない。【提案】(1 つ目に番号を付けない部分)
- 番号は、比べられる版(3.6 節)だけで数える。比べられない版は、日付があっても「YYYY-MM-DD 版」とし、番号を付けない。
- 番号は並べ替えると付け直す。
- `version:` の行は比較の対象にしない。版の違いは版の名前で示す。

### 3.6 比べられない版

- エラー(プロジェクト計画の仕様書 5.3 節・10 章)のある版は、一覧に並べ、エラーの件数と、最初のエラー(行の番号がいちばん小さいもの)の行と文を示す。比べる表からは外す。一覧には「エラー N 件(行: 文)。比較から除外」と示す。【提案】(最初のエラーだけを示す部分)
- `version:` が正しくない場所にある版は、計算部が構文エラーとするので、上と同じ扱いになる。
- `version:` のない版は、版の名前を「version: なし」とし、一覧に「version: がないため比較から除外」と示し、比べる表からは外す。【提案】
- 警告だけの版は、比べられる版として扱う。一覧には警告の件数を示す。

## 4 章 対応づけ

### 4.1 対応名

- FBS・PBS・WBS の要素は、節ごとに、対応名が同じものを対応させる。
- 対応名は、根を除いて、祖先の名前と自分の名前を上から順に `::` でつないだものである。例: WBS の根「カレンダーアプリ」の下の「設計フェーズ」の下の「画面設計」の対応名は `設計フェーズ::画面設計`。
- 名前の大文字と小文字、全角と半角は、計算部と同じく区別する。
- 担当者は名前で対応させる。

### 4.2 根

- FBS・PBS・WBS の根は、名前によらず、前の版の根と後の版の根を対応させる。
- 根の名前が違うときは、節ごとに「FBS の根の名前を変更: 前の名前 → 後の名前」の 1 行を出す(5.3 節)。
- 一方の版にしかない節(FBS・PBS は省略できる)は、その節の要素がすべて増えた、または消えたとする。

### 4.3 移動

- 4.1 節で対応しなかった要素のうち、同じ節の消えた側と増えた側に、名前(対応名ではなく、要素自身の名前)がまったく同じものがちょうど 1 つずつあれば、その 2 つを対応させ、移動とする。
- 同じ名前が片側に 2 つ以上あるときは、移動とせず、消えた・増えたのままにする。
- 移動の判定は、上の要素から順に(前の版の木の順に)行う。【提案】
- 移動した要素の子は、親の対応名が変わるので 4.1 節では対応しない。子にも同じ規則を当てる。
- 移動は、表では「移動(親: 前の親の対応名 → 後の親の対応名)」と示す。親が根のときは「(根)」と書く。

### 4.4 推測しないこと

- 名前の似た要素、属性の似た要素を推測して対応させることはしない。名前の変わった要素は、消えた 1 行と増えた 1 行で出す。

### 4.5 対応した要素の数

前の版と後の版の間で、節ごとに次の形で示す。

- 「対応した数 / 2 つの版のどちらかにある要素の数」(両方にあるものは 1 つと数える)。
- 数える節は FBS・PBS・WBS と担当者である。
- 木のすべての要素(途中の要素を含む)を数え、根は数えない。
- 移動は、対応したと数える。
- 一方の版にしかない節は、対応した数を 0 とする。どちらの版にもない節は出さない。

### 4.6 MOP

- 対応した FBS の要素(移動を含む)どうしで、MOP の文が 1 文字も違わないものを対応させる。
- 同じ要素に同じ文の MOP が複数あるときは、書いた順に対応させる。【提案】
- 対応した MOP のうち、前の版で `mop:`、後の版で `mop*:` のものを「チェック済みになった」、その逆を「チェックを外した」とする。
- 対応しなかった MOP は、増えた・消えたとする。文の書き換えは、消えた 1 行と増えた 1 行になる。
- 増えた・消えた FBS の要素の MOP は、その要素の行に含めて示し、MOP の増えた・消えたには数えない。【提案】

## 5 章 比べる内容

### 5.1 概要(全版)

比べられる版すべてを、一覧の順に列に並べる表とする。行は次のとおり。

| 行(画面の表記) | 値 |
|---|---|
| 版 | 版の名前 |
| ファイル | ファイル名 |
| 開始日 | `start:` |
| 期限 | `end:`(なければ「―」) |
| 全体の休み | `off:` の値(注を除いた書いたままの文。なければ「―」)。太字にするかは、カンマで区切った値を、値の中の空白(`..` の前後を含む)を除いて並べ替えて比べる(空白や並びだけの違いは変わったとしない) |
| クリティカルパスの長さ(日) | 日数(プロジェクト計画の仕様書 6.2 節) |
| 日程の長さ(日) | 担当を入れた日程の暦日数(同 6.4 節) |
| 終了日 | 担当を入れた日程の終わりの日付 |
| メンバー数 | `members:` の人数 |
| FBS 要素数 | FBS の木の要素の数(途中の要素を含み、根は数えない。4.5 節と同じ。FBS がなければ「―」) |
| PBS 要素数 | 同上(PBS) |
| WBS 要素数 | 同上(WBS)。タスク(末端の要素)と途中の要素の合計 |
| タスク数 | タスクの数 |
| 総日数 | タスクの `days:` の合計 |
| MOP 総数 | FBS の要素に書いた MOP の数(`mop:` と `mop*:` の合計。FBS がなければ「―」) |
| 確認した MOP 数 | そのうち `mop*:` の数(FBS がなければ「―」) |
| 警告数 | 警告の数 |

- 左の版と値が違うセルは、太字にする。【提案】
- エラーのある版と版の日付のない版は、列に入れない。【提案】
- 列が多すぎて縮みすぎるときの印刷は、7.5 節による。

### 5.2 比べる 2 つの版

- 比べられる版から 2 つを選ぶ。一覧で前にある方を前の版、後ろにある方を後の版とする。
- 既定は、比べられる版のうち一覧の最初と最後である。利用者が選ぶまでは、版を足す・外す・並べ替えるたびに既定に従う。
- 利用者が選んだ後は、選んだ 2 つを残す。選んだ版が外れたとき(外した、比べられなくなった)は、既定に戻る。
- 比べられる版が 2 つ未満のときは、5.3 節〜5.7 節・5.10 節の代わりに「比較には 2 つ以上の版が必要です」と出す。
- 選んだ 2 つは自動保持に残し、plans には残さない。plans を開いたときは既定の 2 つとする。

### 5.3 比較の要約

5.4 節〜5.7 節の先頭に置く。

- 前の版と後の版の版の名前とファイル名。
- 根の名前の変更(4.2 節)。変更がなければ出さない。
- 対応した要素の数(4.5 節)の表。

### 5.4 WBS

タスク(WBS の末端の要素)について、次の 4 つを示す。ビューの名前は「WBS」とするが、途中の要素は示さない(下の項目)。

1. **増えたタスク**: 対応名、日数、作成者、確認者。
2. **消えたタスク**: 対応名、日数、作成者、確認者。
3. **移動したタスク**: 対応名(後の版)、前の親と後の親。
4. **変わったタスク**: 対応するタスク(移動を含む)で、次の項目の値が違うもの。
   - 日数(`days:`)
   - 作成者(`by:`)・確認者(`review:`)・対象(`for:`): 親から受け継いだ後の値で比べる。
   - 先行(`after:`): そのタスクと祖先に書いた `after:` が指す要素をすべて集めたもので比べる。途中の要素を指したものは、その要素のまま比べ、下のタスクには広げない。
   - 状態(`status:`)
   - メモ(`note:`)

- 対象(`for:`)と先行(`after:`)は、指す要素どうしを 4 章の対応で比べる。指す要素が移動しただけなら、変わったとしない。指す要素の名前が変わった(対応しない)ときは、変わったとする。
- 作成者・確認者・対象・先行は、並びの順によらず、集まりとして比べる。
- 状態の変化は、ほかの項目とは別の列にまとめる。状態だけが変わったタスクは、変わったタスクの一覧には入れず、状態の変化の一覧にだけ入れる。【提案】(状態の変化を別の一覧にする形)
- 表は 1 項目 1 行とし、列は「タスク(対応名)・項目・前の版・後の版」とする。同じタスクの行はまとめたセルにする。【提案】
- タスクが途中の要素になった(子が付いた)ときは、消えたタスクの行に「(子要素ができた)」と添え、子は増えたタスクとする。途中の要素がタスクになった(子がなくなった)ときは、増えたタスクの行に「(子要素がなくなった)」と添える。【提案】(後者)
- WBS の途中の要素の増えた・消えた・移動は、この表には出さず、対応した要素の数(4.5 節)にだけ表れる。【提案】
- 行の並びは、増えたタスクと移動・変わったタスクは後の版の木の順、消えたタスクは前の版の木の順とする。【提案】

### 5.5 日程

- 対応するタスク(移動を含む)について、前の版と後の版の予定の終わり(計算)を日付で並べ、ずれを暦日の日数で示す(後 − 前。遅れは +、早まりは −)。
- 予定の終わり(計算)は、各版の担当を入れた日程の終わりの日(プロジェクト計画の仕様書 6.3 節)とする。
- 表の上に、いちばん遅れたタスクを、タスク(対応名)とずれの表で示す。ずれの最大が同じタスクが複数あれば、すべて示す。ずれの最大が 0 以下なら「遅れたタスクはありません」とする。
- 列は「タスク(対応名)・予定の終わり(計算)前・後・ずれ」とする。【提案】
- 行の並びは後の版の木の順とする。【提案】

**G. 見積もりの変化**

- タスクごとの終了日の表の下に置く。図の上に「比較: 変更前の版 → 変更後の版」を書く(この図だけを保存したときにも、どの版の比較かがわかるようにするため)。
- 対応するタスク(移動を含む)について、前の版と後の版の日数を、タスクごとに 2 本の横棒で並べる(前の版は薄い灰、後の版は黒枠)。差を数で添える。【提案】(棒の形)
- 棒の上に凡例(灰: 変更前、黒枠: 変更後)を置く(図だけを保存しても棒の意味がわかるように)。
- 図の上に、次の 3 つの数を書く。
  - 計画外のタスクの割合: 増えたタスクの日数の合計 ÷ 後の版のタスクの日数の合計(百分率の整数)
  - 消えたタスクの日数の合計
  - 対応するタスクの日数の合計の前・後
- 行の並びは、後の版の木の順とする。【提案】

### 5.6 FBS・PBS・MOP

- FBS の要素: 増えた・消えた・移動。途中の要素を含む。
- PBS の要素: 増えた・消えた・移動。途中の要素を含む。
- FBS の増えた・消えた要素の表は、要素(対応名)と MOP の列とする。MOP は、その要素の MOP をすべて「 / 」で区切って並べ、チェック済みには ✓ を付ける。MOP がなければ「なし」とする(4.6 節)。
- MOP(4.6 節): 増えた・消えた・チェック済みになった・チェックを外した。列は「FBS の要素(対応名)・MOP」とする。【提案】
- 節がどちらの版にもないときは、その部分を出さない。

### 5.7 担当者

- 増えた担当者、消えた担当者。
- 両方の版にいる担当者ごとに、作成の日数(作成者になっているタスクの日数の合計。プロジェクト計画の仕様書 7.7 節)の前・後・差。
- `by:` のないタスクがどちらかの版にあれば、「(担当なし)」の行を置く。【提案】
- 個人の休み(`off:`)が変わった担当者は、前・後の値(注を除いた書いたままの文)を示す。変わったかどうかは、カンマで区切った値を、値の中の空白(`..` の前後を含む)を除いて並べ替えて比べる(空白や並びだけの違いは変わったとしない)。
- 行の並びは後の版の `members:` の順、消えた担当者は前の版の順とする。【提案】

### 5.8 数の書き方

- 日数は、プロジェクト計画と同じく小数を書ける(`1.5` など。末尾の 0 は書かない)。
- 日付は `YYYY-MM-DD` とする。
- 何もないときは「なし」と書く。
- 表の外の文は、一定の幅で折り返す(長い 1 行で図の幅が広がり、印刷で縮みすぎないため)。表のセルの文も、列の幅の上限で折り返す。

### 5.9 推移(全版)

比べられる版すべてで描く図である。比べる 2 つの版の選択には依存しない。上から次の 5 つの図と、5.11 節の表を並べる。

- 横軸は、E を除き、版の並び(比べられる版を一覧の順に等間隔に置く)とし、目盛りの文字は版の名前とする。
- 比べられる版が 1 つのときは、A・D・E・H は点 1 つで描き、I は「変更の多い部分: 2 つ以上の版が必要です」とする。

**A. 終わりの日の推移**

- 縦軸は日付とする。版ごとに、担当を入れた日程の終わりの日(プロジェクト計画の仕様書 6.4 節)を点で打ち、線でつなぐ。
- `end:`(期限)のある版は、その版の位置に期限の印を打ち、期限の印どうしを点線でつなぐ。期限の印と点線は強調の色(えんじ)とする。【提案】(期限の描き方)
- 第 1 層の要素ごとの終わりの線は描かない。【提案】(第 1 層の要素は版によって名前が変わり、線が途切れるため)

**E. バーンアップ(範囲と完了の推移)**

- 横軸は版の日付とし、暦日で等間隔に目盛る。同じ日付の版が複数あるときは、その日付の一覧で最後の版で代表させる。
- 縦軸は日数とし、目盛りは少なくとも 0〜1 日とする(タスクの日数がすべて 0 のときも)。版ごとに「タスクの日数の合計」と「状態が完了のタスクの日数の合計」の 2 本の線を引く。
- 2 本の線は線の形(実線・点線)で区別し、線の端に名前を書く。【提案】

**D. タスクの数とステータスの推移**

- 版ごとに 1 本の棒を立て、タスクの件数を状態(実行前・実行中・完了・問題発生)で積み上げる。棒の高さの全体がタスクの件数である。
- 積み上げの色は、プロジェクト計画のガントチャートと同じ状態の色(実行前は白地に黒枠、実行中は青、完了は薄い灰、問題発生はえんじ)とする。図の上に凡例を置く。
- 積み上げの順は、下から完了・実行中・問題発生・実行前とする。【提案】
- FBS のある版は、棒の下に「MOP チェック済みの件数 / MOP の件数」を書く。【提案】(添え方)

**I. 変更が多かった部分(WBS の第 1 層の要素ごと)**

- 行を第 1 層の要素、列を隣り合う版の組とする表とし、各セルに、その組の間で増えた・消えた・移動した・変わったタスク(5.4 節。状態だけの変化は含めない)のうち、その第 1 層の要素の下にあるものの件数を書き、件数に応じて灰色の濃淡で塗る。【提案】(濃淡の段階)
- タスクがどの第 1 層の要素の下にあるかは、増えた・移動した・変わったタスクは後の版で、消えたタスクは前の版で決める。タスクが根の直下にあるときは、そのタスク自身とする。第 1 層の要素は名前で対応づけ(4.1 節)、名前の変わった要素は別の行とする。
- 行の並びは、その要素が初めて現れた版の木の順とする。【提案】
- 左の欄の幅は、見出し(「WBS の第 1 層」)と行の名前が収まる幅とし、上限を 240 px とする。収まらない名前は先頭の側を「…」で縮める。列の幅は、版の名前が収まる幅(少なくとも 120 px)とする。
- 最後の行に、組ごとの合計を置く。

**H. 担当者ごとの作成の日数の推移**

- 縦軸は日数とし、目盛りは少なくとも 0〜1 日とする。担当者ごとに、各版の作成の日数(5.7 節)を点で打ち、線でつなぐ。その版にいない担当者は、線を切る。
- 線はすべて黒とし、線の右端に担当者の名前を書く。【提案】名前が長いときは、幅 160 px に収まるよう先頭の側を「…」で縮める。
- `by:` のないタスクがある版があれば、「(担当なし)」の線を置く。【提案】

### 5.10 ガントチャート(2 つの版)

比べる 2 つの版(5.2 節)で描くガントチャートの比較である。先頭に 5.3 節の要約を置く。見積もりの変化(G)は 5.5 節に置く。

**F. ガントチャートの比較**

- タスクごとに、前の版の棒と後の版の棒を上下に並べる。前の版の棒は薄い灰、後の版の棒は黒枠とする。【提案】(棒の色)
- 棒の位置は、各版の担当を入れた日程(プロジェクト計画の仕様書 6.3 節)による。目盛りは日付とし、2 つの版の期間をすべて含める。今日の線と状態の色は描かない。
- 休みは、プロジェクト計画のガントチャートに合わせて描く。変更後の版の全体の休みの日は灰の地(#e6e6e2)、変更前の版だけの全体の休みの日は薄い斜線とし、休みがあれば凡例に「全体の休み(変更後)」「変更前だけの休み」を足す。
- 棒は、各版の全体の休みと、そのタスクの作成者の個人の休みの日で切り、続いている日は 1 本にする(プロジェクト計画と同じ)。日数 0 のタスクは、先行が終わった時刻(プロジェクト計画のひし形と同じ位置)を中心に幅 2 px の細い棒を描く。細い棒には縁を付けず、変更前の版は灰の棒と見分けられるよう少し濃い灰(#8a8a86)、変更後の版は黒とする。個人の休みの網は描かない(行が版ごとに分かれ、重ねると読みにくいため)。
- タスクの名前(対応名)が長くて欄に収まらないときは、先頭の側を「…」で縮め、末端の名前と添え書きは残す。【提案】
- 対応するタスク(移動を含む)は 1 行に 2 本の棒、増えたタスクは後の版の棒だけ、消えたタスクは前の版の棒だけを描く。増えた・消えたタスクは、タスクの名前の後ろに「(追加)」「(削除)」と書く。
- タスクがどちらの版にもないときは、「タスクがありません」とする(J も同じ)。
- 行の並びは、対応するタスクと増えたタスクを後の版の木の順に並べ、消えたタスクを前の版の木の順に最後に並べる。【提案】
- 2 つの版の `end:` に縦線を引く(前の版は点線、後の版は実線)。【提案】

**J. 担当者別ガントチャートの比較**

- F の次に置く。
- 担当者の名前の欄の幅の上限は 200 px とし、収まらない名前は先頭の側を「…」で縮める。
- 担当者ごとに 1 行とし、各行を上下 2 段に分けて、上に変更前の版のタスクの棒(薄い灰)、下に変更後の版のタスクの棒(黒枠)を並べる。灰の棒には白い縁を付け、隣り合うタスクが 1 本に見えないようにする。
- 棒にするタスクは、その人が作成者(`by:`)のタスクとする。複数人のタスクは、その全員の行に出す。確認者(`review:`)のタスクは出さない。`by:` のないタスクがどちらかの版にあれば、最後に「(担当なし)」の行を置く(プロジェクト計画の仕様書 7.7 節と同じ)。
- 棒の中には、入る長さのときだけタスクの末端の名前を書く(休みで切れた棒は、いちばん長い切れ目に。日数 0 のタスクの細い棒には書かない)。日数 0 のタスクの細い棒は、隣のタスクの棒に隠れないよう、同じ段のほかの棒の後に描く。棒の位置・目盛り・期限の線・休みは F と同じとする。
- 左に担当者の名前と、作成の日数の「変更前 → 変更後」を置く。
- 行の並びは、変更後の版の `members:` の順とし、変更後にいない人を最後に(変更前の順で)並べる。

### 5.11 状態が初めて変わった版

5.9 節の図の下に置く表である。

- 一覧で最後の比べられる版のタスクごとに、隣り合う版の対応(4 章。移動を含む)をさかのぼってたどり、状態が初めて問題発生になった版と、初めて完了になった版を示す。
- 対応が途切れた(名前が変わった)ところより前はたどらない。
- 列は「タスク(対応名)・初めて問題発生になった版・初めて完了になった版・完了の時期・今の状態」とする。【提案】(列)
  - 完了の時期は「前の版の日付 〜 初めて完了になった版の日付」とする。初めて完了になった版が、たどった中で最も古い版なら「〜 その版の日付」とする。
  - その状態にならなかったときは「―」とする。
- 行の並びは、最後の版の木の順とする。

### 5.12 図から比べる 2 つの版を選ぶ

- A・D・H の版の位置(点・棒・目盛りの文字)を押すと、その版を後の版、その一つ前の比べられる版を前の版にする。最初の版を押したときは、その版を前の版、次の比べられる版を後の版にする。
- I の列(隣り合う版の組)を押すと、その組を前の版と後の版にする。
- 選んだ 2 つは、利用者が選んだもの(5.2 節)として扱う。表示中のビューは変えない。【提案】

### 5.13 改訂履歴(全版)

すべての版の改訂の履歴を、1 つの変更を 1 行にした表で示す。2 つの版の比較ではない。

- 行に入れるのは、比べられる版(3.6 節)だけとし、一覧の順に並べる。各版の行には、その版での改訂、つまり一覧で一つ前の比べられる版からの変化を書く。
- エラーのある版と `version:` のない版は行に入れない。そのような版があれば、表の上に強調の色(えんじ)で警告を出す。
  - 「エラーのため除外: ファイル名、…」
  - 「version: がないため除外: ファイル名、…」
- 列は「版・ファイル・対象・操作・内容」とする。版とファイルは、同じ版の行をまとめたセルにする。内容の列は、ほかの表より広くする(幅の上限 560 px)。【提案】(幅)
- 変化の種類は「対象」と「操作」の 2 列に分けて書く(表計算ソフトに貼ったとき、対象の列で絞り込めるようにするため)。
- 最初の版の行は、対象を「―」、操作を「初版」、内容を「タスク N 件、終了日 YYYY-MM-DD」とする。
- 2 つ目からの版は、変化ごとに 1 行とし、次の順に並べる。同じ対象と操作の中は、タスクと要素は後の版の木の順(消えたものは前の版の木の順)、担当者は `members:` の順とする。

| 順 | 対象 | 操作 | 元の節 |
|---|---|---|---|
| 1 | タスク | 追加・削除・移動・変更(この順) | 5.4 節 |
| 2 | タスクの進捗 | 変更 | 5.4 節 |
| 3 | FBS 要素、PBS 要素(この順) | 追加・削除・移動(この順) | 5.6 節 |
| 4 | MOP | 追加・削除・確認・確認取り消し(この順) | 4.6 節 |
| 5 | FBS の根の名前・PBS の根の名前・WBS の根の名前(この順) | 変更 | 4.2 節 |
| 6 | 開始日・期限・全体の休み(この順) | 変更(概要の表の値が変わったとき) | 5.1 節 |
| 7 | メンバー | 追加・削除(この順。`members:` の担当者の増減。タスクへの割り当ての変化は「タスク 変更」に書く) | 5.7 節 |
| 8 | メンバーの休み | 変更(両方の版にいるメンバーの個人の休みが変わったとき) | 5.7 節 |
| 9 | 終了日 | 変更(担当を入れた日程の終了日が変わったとき) | 5.5 節 |

- 内容の書き方は、対象と操作ごとに次のとおりとする。メンバーの追加・削除は担当者の名前とする。
  - タスク・要素の追加・削除・移動: 対応名。移動は「対応名(親: 前の親 → 後の親)」。子要素ができた・なくなったときの添え書きは 5.4 節と同じ。
  - タスク 変更: 「対応名(項目 変更前 → 変更後、…)」。項目は 5.4 節の変わったタスクの項目(状態を除く)。
  - タスクの進捗 変更: 「対応名(変更前 → 変更後)」。
  - FBS 要素 追加・削除: 対応名に、その要素の MOP を「(MOP: 文 / 文)」と添える(機能とテストがいつ足されたかを見られるようにするため)。MOP がなければ添えない。
  - MOP の各操作: 「FBS の要素の対応名: MOP の文」。
  - 根の名前 変更: 「変更前の名前 → 変更後の名前」。
  - 開始日・期限・全体の休み 変更: 「変更前 → 変更後」。期限と全体の休みがないときは「なし」と書く。全体の休みは注を除いた書いたままの文とする。
  - メンバーの休み 変更: 「名前(変更前 → 変更後)」。値の書き方は 5.7 節と同じ。
  - 終了日 変更: 「YYYY-MM-DD → YYYY-MM-DD(差の暦日)」。
- 全体の休みとメンバーの休みは、5.7 節と同じく、空白や並びだけの違いを変更としない。
- 前の版から何も変わっていない版(注や空白だけが違う版)は、対象を「―」、操作を「変更なし」とする 1 行を置く。
- 行を押すと、その版を後の版、一覧で一つ前の比べられる版を前の版にする(5.12 節と同じ。最初の版の行は、その版と次の版)。
- 表なので、題の右の「コピー」でコピーできる(6.2 節)。

## 6 章 画面

画面の構成と配色・字体は、プロジェクト計画に合わせる。【提案】

- **上の帯**: 新規、開く、上書き保存、別名で保存、印刷 / PDF、ファイル名、ビューの選択欄、使い方。保存したことの表示と、自動保持(7.6 節)の警告もここに出す。
- **左**: ファイルの操作だけなので、既定の幅は狭くする(画面の 22%、最小 220 px)。【提案】(幅の値)
  - 一覧(3.4 節)。各版に、版の名前・ファイル名・警告の件数またはエラー・並べ替えのボタン・外すボタンを示す。
- **右**: ビュー。2 つの版を比較するビュー(WBS・日程・FBS・PBS・MOP・メンバー・ガントチャート)では、比べられる版が 2 つ以上あるとき、ビューの上に比較する版の帯(「比較 変更前 [選択欄] → 変更後 [選択欄]」)を置く。
  - 変更後の選択欄の隣に、少し間を空けて薄い灰色の文字「プリセット」を置き、続けて「初版 → 最新版」「前の版 → 最新版」のボタンを置く。初版・最新版は、比べられる版を一覧の順に並べたときの最初と最後とする(警告だけの版は含め、エラーのある版と `version:` のない版は含めない)。比べられる版が 2 つだけのときは、どちらも同じ組を選ぶ。
  - 「初版 → 最新版」は既定の組(5.2 節)に戻す。版を足すと、最新版に合わせて変わる。
  - 「前の版 → 最新版」は、最新版とその一つ前の比べられる版を選ぶ。選択欄で選んだのと同じく、利用者が選んだもの(5.2 節)として扱う。すべての版を示すビュー(概要・改訂履歴・推移)では帯を出さない。帯は画面の部品とし、保存した画像や印刷には出さない(どの版の比較かは、図の中の「比較: … → …」で示す)。
- **仕組み**:
  - 左右の分割バー
  - ドラッグ・アンド・ドロップでの読み込み
  - 「使い方」のダイアログ(枠外のクリックで閉じる)。比べ方の規則(名前で対応づけること、名前の変更は消えた・増えたの 2 行になること、移動、同じ日付の版の並べ替え、予定の終わりは計算した予定であること)を説明し、`.plan` の書き方はプロジェクト計画(plan.sapp.jp)へのリンクで示す。
  - フッター
- 「書き方」「例を読み込む」は置かない。

### 6.2 表のコピーと保存

- 各表の題の右に「コピー」「SVG」「PNG」「PDF」のボタンをこの順に置く。「SVG」「PNG」は、その表を 1 つずつ画像で保存し、「PDF」はその表だけを同じ大きさの紙で印刷する(7.3 節・7.4 節)。
- 「コピー」は題の文字のすぐ右に置き(題の文字のすぐ右に置き、ボタンの文字と題の文字の見た目の中心をそろえる。中心は、フォントによって変わる上下の余白ではなく、文字の基準線から求める)、表をタブ区切りの文字でクリップボードに写す。ボタンは図の上に重ねて置く画面の部品とし、SVG には含めない(保存した画像や印刷には出ない)。画面の上の帯には置かない。
- 1 行目は見出しの行とする。まとめたセルは、各行に同じ値を書く。【提案】
- 行の区切りは LF とする。セルの値にタブや改行が含まれるときは、空白 1 個に置き換える。【提案】
- 写したら「コピーしました」を 2 秒出し、元の文に戻す。続けて押したときも、元の文に戻す。写せなかったときは、その旨を出す。
- CSV のファイルの保存は設けない。
- コピーの対象は、画面に表として描いた表だけとする。5.5 節・5.9 節・5.10 節の図の元の数はコピーの対象にしない。

## 7 章 保存と読み込み

### 7.1 plans の形式

- JSON とし、文字コードは UTF-8(BOM なし)、改行は LF とする。拡張子は `.plans`。
- 中身は、一覧の順に並べた各版のファイル名とテキストである。並びが手で並べ替えた順を兼ねる。
- `version:` は持たない。
- 比べる 2 つの版の選択など、見ている状態は入れない。
- 形は次のとおりとする。キーの順と字下げ(空白 2 個)を固定し、同じ一覧からは同じファイルを書く。【提案】

```
{
  "format": "projalysis-plans",
  "files": [
    {
      "name": "team_a.plan",
      "text": "version: 2026-04-20\nstart: 2026-04-23\n..."
    },
    {
      "name": "team_a_2.plan",
      "text": "..."
    }
  ]
}
```

- `format` が違う、または形が合わないファイルは、読めないことを知らせて読まない。【提案】
- エラーのある版も plans に入れる。

### 7.2 上書き保存・別名で保存

プロジェクト計画の仕様書 9 章の上書き保存・別名で保存に合わせる。違う点は次のとおり。

- 保存するのは plans である。名前の候補は今のファイル名、なければ「一覧の最初の版のファイル名から拡張子を除いたもの.plans」とする。【提案】(名前の候補)
- 上書きの先は、最初に開いた `.plans` とする。`.plan` から始めた一覧と、プロジェクト計画の SVG から始めた一覧には上書きの先がなく、上書き保存では保存先を尋ねる。
- 上書きの先のある一覧に別の plans を足した後、最初に上書き保存したとき(Ctrl+S を含む)は、アプリの中のダイアログで「足した plans(足した plans の名前を「、」で区切って並べる)の版も、名前.plans に書き込みます。」と出し、「上書き保存」「別名で保存」「やめる」から選ばせる。一度「上書き保存」を選んだら、次に plans を足すまで出さない。`.plan` を足しただけのときは出さない。
- 足す・外す・並べ替えは保存していない変更とし、ファイル名の後ろに ` *` を付ける。
- 「新規」は一覧を空にする。保存していない変更があれば、空にしてよいかを確かめる。
- 書き込むテキストは、改行を LF とし、BOM を付けない。

### 7.3 SVG

- 図のあるビュー(推移・日程・ガントチャート)では、各図の題の右に「SVG」「PNG」「PDF」のボタンを置き、図を 1 つずつ保存できる(PDF は 7.4 節)(ボタンは 6.2 節の「コピー」と同じく図に含めない)。保存する図には図の題を付ける(F・J・G には変更前と変更後の版、G には 5.5 節の 3 つの数も付ける)。ファイル名は「元の名前_ビュー_図の識別子」とする(例: `team_a_trend_status.svg`)。
- 表は、各表の題の右の「SVG」「PNG」「PDF」で 1 つずつ保存できる(6.2 節。PDF は 7.4 節)。保存する表には題を入れない(報告書では題を表の上に書くため)。ファイル名は「元の名前_ビュー_表の題」とする。表の題は件数を除いたものとし、ファイル名に使えない文字と空白は「_」にする(例: `team_a_tasks_追加したタスク.svg`)。
- 元の名前は、今のファイル名、なければ一覧の最初の版のファイル名から拡張子を除いたものとする。元の名前も、ファイル名に使えない文字と空白は「_」にする。
- 保存する SVG には、読み込んだ版を埋め込まない(正本は plans だけとする)。そのため、保存した SVG をプロジェクト分析で開いても版は戻らない。
- 表示中のビュー全体を 1 枚の画像で保存することはしない(図と表を 1 つずつ保存するか、印刷 / PDF を使う)。
- 5 章の図の記号(A〜J)は、この仕様書の中で図を指すためだけに使い、画面の題・保存する図・ファイル名には出さない。画面の題と識別子は次のとおりとする。

| 記号 | 画面の題 | 識別子 |
|---|---|---|
| A | 終了日の推移 | `end` |
| E | バーンアップ(横軸は版の日付) | `burnup` |
| D | タスク数と進捗の推移 | `status` |
| I | 変更の多い部分(WBS の第 1 層ごとのタスクの変更数) | `changes` |
| H | 担当者ごとの作成の日数 | `effort` |
| F | ガントチャートの比較 | `gantt` |
| J | 担当者別ガントチャートの比較 | `gantt-people` |
| G | 見積もりの変化 | `estimate` |

### 7.4 PNG・PDF

- 図と表を 1 つずつ PNG で保存できる(7.3 節と同じく、題の右の「PNG」)。中身とファイル名の形は SVG と同じとし、解像度は 2 倍とする。
- 題の右の「PDF」は、その図または表だけを、それと同じ大きさの紙(余白 0)で印刷する。印刷の画面で「PDF に保存」を選ぶと、余白のないベクター形式の PDF 1 ページになる(TeX などにそのまま貼れる)。中身は SVG と同じとする。印刷の画面のファイル名の候補は、SVG と同じ形(拡張子なし)とする。アプリの中で PDF のファイルを作ることはしない。
- 印刷の領域に入れる図(全体の印刷と「PDF」)は、属性の `id` と `url(#…)` に印を付け(タスクの名前などの文の中に書いた `url(#…)` は変えない)、画面の図と重ならないようにする(重なると、印刷では見えない画面の側の模様を指し、斜線などが消えるため。プロジェクト計画と同じ)。全体の印刷の前には、「PDF」の紙の指定が残っていれば戻す。
- 保存する SVG にも、同じ紙の大きさの指定(`@page`)を入れる。保存した SVG をブラウザで開いて印刷しても、同じ大きさの PDF になる。
- 紙の大きさの指定は Chrome・Edge で確かめている。Safari では効かないことがある。

### 7.5 印刷 / PDF

- ビューをすべて、6.1 節の順に、1 つ以上のページに印刷する。比べられる版が 2 つ未満なら、概要だけを印刷する。
- ページの向きは横とする。【提案】
- A4 横の 1 ページに収めると元の大きさの半分より小さくなる表は、ページを分ける(判定はプロジェクト計画の仕様書 9 章と同じ)。
  - 5.4 節〜5.7 節の表は、行で区切り、各ページに見出しを付ける。まとめたセルはページの境目で切って描く。比較の要約は最初のページにだけ置く。
  - 表の題は、表の見出しの行と最初の行と同じページに置く。1 行だけでページに収まらない行は、その行を区切らずに置き(半分より小さく縮むことがある)、題だけのページは作らない。
  - 概要の表は列(版)で区切り、各ページの左に行の見出しの列を置く。
  - 推移のビューは、図 1 つと 5.11 節の表を、それぞれ別のページにする。版が多くて図が半分より小さくなるときは、横軸の版で区切ってページを分ける。5.11 節の表は行で区切る。【提案】
  - 日程のビューは、G の題より前を表と同じく行で区切り、G を別のページにして行で区切る(続きのページの題は「見積もりの変化(続き)」)。G の最初のページには「比較: … → …」を置く。【提案】
  - ガントチャートのビューは、比較の要約を独立したページにし、F・J をそれぞれ別のページにして行で区切る。F・J の最初のページは、「比較: … → …」と図の題と図だけとする(PDF から図だけを切り出しやすくするため)。【提案】
- 各ページには表だけを置き、ファイル名や日付などの文字は足さない。ページの余白は 0 とし、表の周りの空き(10 mm)はページの内側に取る(プロジェクト計画と同じ)。

### 7.6 自動保持

- 一覧(各版のファイル名とテキスト、並び)・ファイル名・保存していない変更があるか・比べる 2 つの版と、それを利用者が選んだか(5.2 節)・表示中のビュー・7.2 節の警告を出すかどうかと足した plans の名前を、変わるたびに、このブラウザの `localStorage` に保持する。どこにも送信しない。【提案】(表示中のビュー)
- 開いたときは、保持してある内容を続きとして開く。一覧は 3.4 節の順に並べ直す(同じ日付の中は保持した順のまま)。なければ空で開く。
- 7.2 節の警告を出すかどうかも、開き直したときに戻す(ファイル操作機能のないブラウザでは、ファイル名が上書きの先として残るため)。
- ページを開き直すと上書きの先は忘れ、次の上書き保存では保存先を尋ねる(プロジェクト計画と同じ)。
- 保持に失敗したとき(容量超過など)は、上の帯に警告を出す。一覧が空のときは出さない。
- 別のタブで同じ一覧が変わったときは、上の帯に警告を出す。
